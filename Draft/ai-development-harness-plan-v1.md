## 1. 제품 정의

### 1.1 한 문장 정의 **[확정]**

> 개발 기획서를 주면 하네스가 Phase로 나누고, 사용자가 시작을 지시하면 기획서에 정한 언어·도구로 환경을 세팅해 개발·테스트·리뷰를 진행한다. 끝나면 산출물을 안내하고, 사용자가 인수하면 Phase를 완료 처리하는 로컬 개발 도구.

### 1.2 존재 이유 **[확정]**

AI가 작성한 코드에서 생기는 문제를 줄인다. 각 문제를 막는 방법은 6장에 상세히 적는다.

| 문제 | 하네스가 막는 방법 |
|---|---|
| 잘못된 코드 (요구사항 오해, 동작하지 않는 코드) | 요구사항 대응표, 하네스가 직접 실행한 테스트, 독립 Reviewer |
| 중복 코드 | 구현 전 기존 코드 탐색, 중복 탐지 검사, Reviewer의 중복 확인 |
| 낮은 품질 | 언어별 품질 검사(포맷·린트·타입), 프로젝트 규칙, Reviewer 품질 기준 |
| 거짓 완료 (테스트 삭제·약화, 미실행을 통과로 보고) | 하네스가 결과 판정, 테스트 목록 비교, 기준 완화 차단 |

### 1.3 역할 분담 **[확정]**

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| AI (Planner·Developer·Reviewer) | 기획서 해석, 기술 구성 반영, 세팅 명령 작성, 코드·테스트 작성, 리뷰 | 결과 판정, 승인, 정책·검사 기준 변경 |
| 하네스 | 흐름 순서, 승인 확인, 명령 실행 중개, 결과 판정, 기록, Phase 문서 갱신 | 특정 언어 지식 보유, 코드 작성 |
| 사용자 | 기획서 작성, 시작 지시, 위험 동작 승인, 결과 확인·인수 | 매 단계 명령 조작 |

**핵심 원칙:** 하네스 코드에는 특정 언어·프레임워크 지식을 넣지 않는다. 언어 지식은 기획서와 AI가 가진다. 하네스는 공통 규약(명령 종료 코드, 표준 테스트 보고서, 파일 해시)으로만 판단한다. 따라서 지원 언어 목록을 관리하지 않는다.

## 2. 기본 흐름 **[확정]**

```text
① 사용자가 기획서를 준다
② 하네스가 기획서를 읽고 Phase를 구성하고 Phase 문서를 만든다 (Phase 0: 환경 준비 포함)
③ 사용자가 검토하고 "시작"을 지시한다
④ Phase 0: 기획서의 기술 구성으로 환경을 세팅하고 기본 검사가 통과하는지 확인한다
⑤ 개발 Phase: Task별 개발 → 테스트·품질 검사 → 리뷰 → 필요하면 수정
⑥ Phase 통합 검증 후 산출물을 안내한다
⑦ 사용자 OK → 인수 → Phase 문서 완료 처리 → 다음 Phase 상세 계획 제시
   사용자 수정 요청 → 같은 범위 수정 또는 계획 변경
```

### 2.1 사용자 결정 지점 **[확정]**

사용자가 직접 하는 일은 아래 네 가지로 제한한다. 그 사이의 내부 단계는 하네스가 이어서 진행한다.

| 결정 | 시점 | 의미 |
|---|---|---|
| 기획서 제공 | 처음 | Phase 구성 요청 |
| 시작 | Phase 계획 검토 후 | 현재 Phase 계획 승인과 실행 지시를 한 번에 한다. 계획에 사용자가 골라야 할 항목(예: 기술 구성 선택지)이 있으면 이때 고른다 |
| 위험 동작 승인 | 실행 중 필요할 때 | 계획에 없는 설치, 외부 네트워크 사용, 시스템 변경 |
| 인수 또는 수정 요청 | 산출물 안내 후 | Phase 완료 또는 재작업 |

- **Phase 0과 개발 Phase는 각각 따로 시작하고 따로 인수한다 [확정].** 세팅이 끝나면 멈추고 결과를 안내한다. 사용자가 인수한 뒤에 첫 개발 Phase를 시작한다.
- **계획만 따로 고치는 기능은 두지 않는다.** 이 하네스는 기획이 완료된 기획서를 전제로 하므로, 기획서가 유일한 근거다. 계획이 기획서와 다르면 원인에 따라 처리한다. 기획서가 모호했다면 기획서를 고친 뒤 `plan`을 다시 실행한다. AI가 잘못 읽었다면 `plan`만 다시 실행한다. 어느 경우든 새 계획 버전이 생기고 이전 버전은 보존된다. 계획만 고치면 기획서와 계획이 어긋나서, 다음 Phase를 상세화할 때 그 수정 내용이 사라지기 때문이다.
- 무응답은 대기 상태다. 시간이 지나도 자동 승인하지 않는다.
- 승인은 승인한 계획·코드 버전에 묶인다. 내용이 실질적으로 바뀌면 다시 승인받는다. 바뀌지 않았으면 반복 승인받지 않는다.

### 2.2 명령 예시 **[확정]**

| 명령 | 동작 |
|---|---|
| `dev-harness plan <기획서>` | ①–② 기획서를 읽고 Phase 구성·문서 생성. 다시 실행하면 새 계획 버전을 만든다 |
| `dev-harness start` | ③–⑥ 현재 계획 승인 후 세팅·개발·검증·산출물 안내까지 진행 |
| `dev-harness status` | 진행 상황과 대기 중인 승인 표시 |
| `dev-harness approve <항목>` | 실행 중 요청된 위험 동작 승인 |
| `dev-harness accept` / `dev-harness feedback` | ⑦ 인수 또는 수정 요청 |
| `dev-harness resume` | 중단 후 재개 |

## 3. 기획서 입력과 Phase 구성

### 3.1 기획서에서 읽는 것

- 기능 요구사항과 제약조건.
- **기술 구성 [확정]:** 언어와 런타임 버전, 프레임워크, DB, 테스트 도구. 기획서에 적혀 있으면 그대로 따른다.
- **기술 구성이 없거나 모호할 때 [확정]:** Planner가 추천안 1개와 대안 1–2개를 각각의 이유와 함께 제시한다. 사용자는 Phase 0을 시작할 때 하나를 고른다. 하네스가 임의로 정해 진행하지 않는다. 고른 결과는 Phase 문서에 사용자 결정으로 기록하고, 이후 계획의 근거로 쓴다.
- **기존 프로젝트일 때 [확정]:** 기존 코드의 언어와 구성을 확인한다. 기획서와 충돌하면 질문하고 중단한다.
- 구현을 막는 결정이 빠져 있으면 추측하지 않고 질문한다.

### 3.2 Phase 구성 규칙 **[확정]**

- **Phase 0 (환경 준비)는 항상 첫 Phase로 계획하고 생략하지 않는다.** 이미 준비된 프로젝트라면 확인만 하는 짧은 Phase가 된다(4.4).
- Phase 1–N은 기능 개발 단계다. 각 Phase는 사용자가 결과를 직접 확인할 수 있는 단위로 나눈다.
- 전체 Phase의 목표·순서·완료 기준은 처음에 작성한다. Task 상세는 현재 Phase만 작성하고, 다음 Phase는 이전 Phase를 인수한 뒤 상세화한다.
- 기획서에 Phase 구분이 이미 있으면 그대로 따른다.

### 3.3 요구사항 대응표 (0.4 유지)

- 기획서의 모든 요구사항을 구현·재사용·연기·제외로 분류하고, 각각 근거를 적는다.
- 재사용은 계획 시점의 판단일 뿐이다. 해당 Phase를 인수할 때 실제 검사 결과로 확인한다.
- 조사하지 않은 항목은 "확인 필요"로 표시한다.

### 3.4 Phase 문서 **[확정]**

- 위치는 프로젝트의 `Phase/` 폴더다. `Overview.md`와 `PhaseN_Name.md`를 phase-doc 템플릿으로 만든다.
- 하네스가 자동으로 바꾸는 범위는 상태(미시작·진행 중·완료), 완료일, Task 상태, 검증 결과 요약과 근거 링크, 변경 이력 행으로 한정한다. 사용자가 작성한 나머지 내용은 바꾸지 않는다.
- "완료" 표시는 사용자 인수 기록이 있을 때만 한다. Phase 0도 다른 Phase처럼 사용자가 인수해야 완료된다 **[확정]**.
- 계획을 수정하면 이전 버전을 보존한다.
- Phase 문서는 영문과 국문을 반드시 모두 작성하고, 갱신할 때 두 언어를 함께 맞춘다.

## 4. Phase 0: 환경 준비

### 4.1 목표 **[확정]**

기획서에 적힌 기술 구성으로 개발과 검증을 실제로 할 수 있는 상태를 만든다.

**완료 조건 [확정]:** 5장의 검사 계약을 모두 충족하고, 테스트가 1개 이상 실제로 실행되어 통과하고, 기준선(4.2)을 기록한 뒤, 사용자가 결과를 인수해야 한다.

### 4.2 세팅 계획에 포함할 내용 **[확정]**

Planner가 작성하고 사용자가 "시작"으로 승인한다.

| 항목 | 내용 |
|---|---|
| 런타임·도구 | 언어, 버전, 패키지 관리자, 빌드 도구 |
| 설치·초기화 명령 | 실행할 명령 목록. 명령마다 네트워크 사용 여부와 관리자 권한 필요 여부를 적는다 |
| 프로젝트 골격 | 신규 프로젝트: 생성할 파일·폴더. 기존 프로젝트: 추가할 설정 또는 변경 없음 |
| DB | 종류, 로컬 실행 방법, 테스트용 DB를 개발 DB와 분리하는 방법 |
| 검사 명령 | 테스트와 품질 검사. 5장 검사 계약 형식으로 적고, 검사 설정 파일 목록과 검사 회피 주석 패턴도 함께 적는다 (6.4) |
| 잠금 파일 | 버전을 고정한 잠금 파일 목록. 하네스가 변경을 추적한다 (아래 버전 고정) |
| 프로젝트 규칙 | 코드 스타일, 구조, 오류 처리, 테스트 규칙 (6.3) |
| 기준선 | 시작 시점의 테스트 목록, 기존 중복, 기존 품질 검사 위반 상태, 기존 검사 회피 주석. 이후 "새로 생긴 문제"를 가려내는 기준이 된다 (6.5) |

**버전 선택 [확정]**

- 기획서에 버전이 있으면 그대로 따른다.
- 기획서에 언어만 있고 버전이 없으면, Phase 0 계획에 추천 버전과 이유를 적고 "이대로 할지, 원하는 버전이 있는지"를 묻는다. 사용자는 Phase 0을 시작할 때 답한다. 3.1의 기술 구성 선택과 같은 시점이다.
- 묻는 대상은 런타임, 프레임워크, DB 같은 주요 구성으로 한정한다. 일반 라이브러리는 추천 버전으로 정해 설치 목록에 보여주고 따로 묻지 않는다.
- 추천 이유에는 장기 지원(LTS) 여부, 지원 종료 시점, 다른 구성과의 호환을 적는다. AI가 아는 버전 정보는 오래됐을 수 있으므로, 그 버전이 실제로 설치되고 실행되는지 Phase 0에서 확인한다.

**버전 고정 [확정]:** 정한 버전은 정확한 번호로 고정하고 잠금 파일(예: `package-lock.json`, 버전을 고정한 `requirements` 파일)을 함께 만든다. 같은 명령으로 나중에 다른 버전이 설치되는 일을 막기 위해서다. Phase 0에서 잠금 파일 목록을 등록한다.

**버전 변경 [확정: H3]:** 버전은 사용자 승인 없이 바뀌지 않는다. 대상에 따라 처리가 다르다.

- 주요 구성(런타임, 프레임워크, DB): 하네스는 바꾸지 않는다. 올리기·내리기는 사실상 별도의 이전 작업이므로, 필요하면 사용자가 직접 한다.
- 일반 라이브러리: 새 라이브러리를 추가하다 기존 버전과 충돌하면, AI는 멈추고 이유와 대안(다른 라이브러리 사용, 기존 버전 변경 등)을 제시한다. 사용자가 승인하면 하네스가 변경 명령을 실행하고, 기본 검사를 다시 통과한 뒤 진행한다. 승인이 없으면 바꾸지 않는다.
- 하네스는 등록된 잠금 파일의 변경을 추적해 보고서에 표시한다. 하네스는 잠금 파일 형식을 모르므로, 기존 항목의 버전이 바뀌었는지는 Reviewer가 확인한다. 승인 없이 기존 버전이 바뀌었으면 필수 지적이다.
- 사용자가 직접 버전을 바꾸면, 하네스는 다음 Phase를 시작할 때 이를 알린다. 기본 검사를 다시 통과한 뒤에 시작한다.

### 4.3 실행 규칙 **[확정]**

- 승인된 명령 목록만 실행한다. 목록에 없는 명령은 실행하기 전에 승인을 요청한다.
- **관리자 권한이 필요한 작업은 실행하지 않는다 [확정: 회사 정책].** 시스템 서비스 설치나 전역 설정 변경이 필요하면 정확한 수동 절차를 안내하고, 사용자가 처리한 뒤 확인 검사를 거쳐 재개한다.
- 프로젝트 안이나 사용자 범위의 설치를 우선한다. 예: 프로젝트 가상환경, 로컬 패키지 폴더, 포터블 런타임.
- 기존 파일은 덮어쓰지 않는다. 신규 골격을 만들 때는 생성할 파일 목록을 먼저 보여준다.
- 설치 명령이 성공했다는 것만으로 세팅 완료로 보지 않는다. 검사 계약을 충족해야 완료다.
- 기존 프로젝트의 기본 검사가 실패하면 원인을 보고한다. 이후 (a) 승인을 받아 Phase 0에서 고치거나 (b) 사용자가 직접 고친 뒤 재개한다. 실패를 자동으로 허용하지 않는다.
- 도구 미설치나 권한 문제를 코드 수정 재시도로 해결하려 하지 않는다.
- **패키지 다운로드:** 회사 네트워크에서 npm(TypeScript)은 동작하는 것을 사용자가 확인했다. Python(pip)은 이 하네스를 설치할 때 사용해 왔다. Java(Maven·Gradle)는 확인되지 않았으므로 12장 1단계에서 실제로 시험한다. 막혀 있으면 회사 프록시나 사내 저장소 설정을 Phase 0 계획에 포함한다. 그래도 안 되면 원인과 필요한 조치를 안내하고 멈춘다.

### 4.4 세팅이 필요 없는 프로젝트 **[확정]**

개발 환경이 이미 갖춰진 기존 프로젝트도 있다. 이 경우에도 Phase 0은 생략하지 않고 필요한 만큼만 수행한다. 하네스를 쓰려면 기준선 기록과 검사 계약 확인이 반드시 필요하기 때문이다.

| 형태 | 해당 프로젝트 | Phase 0에서 하는 일 |
|---|---|---|
| 전체 세팅 | 신규 프로젝트 | 설치, 골격 생성, 검사 명령, 프로젝트 규칙, 기준선 |
| 부분 세팅 | 기존 프로젝트이지만 빠진 것이 있음 (예: 표준 테스트 보고서를 출력하지 않음, 린트 없음) | 빠진 항목만 세팅하고 기준선 기록 |
| 확인만 | 기존 프로젝트이며 모두 갖춤 | 설치나 코드 변경 없이 하네스가 검사를 실행하고 기준선을 기록한 뒤 결과 안내 |

- 어떤 형태인지는 Planner가 제안한다. 다만 "이미 준비됨"을 AI의 판단만으로 확정하지 않고, 하네스가 검사를 실제로 실행해 확인한다.
- "확인만" 형태는 AI 개발 호출이 없어 짧게 끝난다. 결과를 확인한 뒤 사용자가 인수한다.

## 5. 검사 계약: 언어와 무관한 결과 판정 **[확정]**

하네스가 언어를 몰라도 결과를 판정할 수 있게 하는 공통 규약이다. Phase 0에서 언어에 맞는 명령을 이 규약에 맞춰 세팅한다.

| 항목 | 규칙 |
|---|---|
| 실행 | 명령(argv), 작업 폴더, 제한 시간을 등록한다. 하네스가 직접 실행하고 종료 코드와 출력을 기록한다 |
| 테스트 결과 형식 | 표준 테스트 보고서(JUnit XML)를 파일로 출력한다. 대부분의 테스트 도구가 지원한다. 예: pytest, Jest·Vitest, Gradle·Maven, dotnet test, Go(gotestsum), Rust(cargo-nextest) |
| 테스트 통과 조건 | 종료 코드 0, 보고서 존재, 실행된 테스트 1개 이상, 실패·오류 0개를 모두 만족해야 한다 |
| 테스트 목록 비교 | 이전에 통과한 테스트가 사라지거나 건너뛰기로 바뀌면 보고하고, Reviewer가 반드시 확인한다 |
| 건너뛴 테스트(skip) | 기준선에 있던 skip은 허용한다. 새로 생긴 skip(새 테스트의 skip, 통과하던 테스트의 skip 전환)은 보고서에 표시하고 Reviewer가 반드시 확인한다 |
| 품질 검사 | 포맷, 린트, 타입 검사, 빌드. 종료 코드로 판정한다 |
| 중복 검사 | 6.2 |
| 예외 | 표준 보고서를 낼 수 없으면 테스트 수를 확인할 수 없으므로, 그 검사는 "미확인"이며 그대로는 인수할 수 없다. 사용자가 해당 검사를 수동 확인 항목으로 바꾸는 것을 승인하면, 직접 확인한 결과를 기록한 뒤 인수할 수 있다 |

### 5.1 검사 실행 격리 **[확정: 방식 C]**

원칙(0.4 유지): 검사 중 실행되는 프로젝트 코드가 하네스의 기록·승인·정책을 바꿀 수 없어야 한다.

현재 구현의 AppContainer 격리는 Python 런타임 하나를 복사하는 방식이라 다른 언어로 그대로 넓힐 수 없다. 아래 세 방식 중 C를 선택했다.

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 런타임별 AppContainer 확장 | 변경을 실행 중에 차단한다 | 런타임마다 복사·권한 작업이 필요하고, DB 연결 같은 로컬 네트워크가 제한된다 |
| B. 일반 사용자 권한 실행 + 변조 탐지 | 모든 언어에서 동작한다 | 차단이 아니라 사후 탐지다 |
| C. 혼합: 가능하면 A, 불가하면 B. 보고서에 격리 수준을 표시 | 범용이면서 가능한 곳은 강하게 보호한다 | 구현이 두 갈래가 된다 |

**결정:** Python 프로젝트는 기존 AppContainer 격리를 그대로 쓴다. 그 밖의 언어와, 로컬 네트워크(DB 서버 등)가 필요한 검사는 B로 실행한다. 보고서에는 격리 수준을 표시한다. 기존 AppContainer 경로가 프로젝트 자체 의존성(가상환경)을 쓰는 Python 프로젝트에서도 동작하는지는 12장 2단계에서 확인한다.

**변조 탐지 방법 (B·C):** 하네스는 실행 기록의 최신 해시를 메모리에 보관하고 명령이 끝날 때마다 대조한다. 자기 설치본도 매니페스트 해시로 확인한다. 검사 결과는 하네스가 새로 만든 폴더에서만 읽는다. 불일치가 발견되면 중단한다.

## 6. 코드 품질 장치

### 6.1 잘못된 코드 방지 **[확정]**

- 요구사항 대응표를 Task 완료 기준과 테스트로 연결한다.
- Developer는 테스트를 함께 작성하되, 실행과 판정은 하네스가 한다. Developer의 "테스트 통과" 자기 보고는 근거로 쓰지 않는다.
- Reviewer는 별도 세션에서 요구사항·코드·테스트를 대조하고, 테스트가 의미 있는 검증인지 확인한다.
- 5장의 테스트 목록 비교로 테스트 삭제·약화를 잡는다.
- 필수 지적이 해결됐는지는 후속 리뷰와 재검사로만 판정한다.

### 6.2 중복 방지 **[확정]**

- **구현 전 탐색:** Developer와 Reviewer는 프로젝트 전체를 읽고 검색할 수 있다(읽기 전용). 사용자가 관련 파일을 하나하나 지정하지 않는다. 단, 비밀값 파일은 읽지 못한다 (7.1).
- **계획 단계:** Planner가 재사용할 기존 기능을 대응표와 Task에 기록한다.
- **Developer 응답:** 확인한 기존 유사 코드와, 재사용했는지 새로 작성했는지 그 이유를 반드시 포함한다.
- **중복 탐지 검사 [확정: 하네스 내장, 보조 수단]:** 하네스에 내장한 탐지기가 언어 문법 지식 없이 단어(토큰) 단위로 비교해, 그대로 복사한 코드 덩어리를 찾는다. 공백과 줄바꿈 차이는 무시한다. 기준선과 비교해 이번 변경에서 새로 생긴 중복만 보고하고, Reviewer의 근거로 넘긴다. 탐지기는 막거나 합치지 않으며, 합칠지는 Reviewer가 판단한다. Developer와 Reviewer가 모두 AI이므로, AI가 아닌 기계적 근거를 하나 남기기 위해 둔다.
- **탐지기 범위 [확정: H1]:** 첫 버전은 그대로 복사한 코드만 찾는다. 이름만 바꾼 복사나 비슷한 로직은 찾지 못하며, 이 한계를 보고서에 적는다. 탐지 정확도는 출시 조건이 아니다. 중복 방지의 주력은 구현 전 탐색, 재사용 근거, Reviewer 확인이다. 정확도가 부족하면 외부 도구(예: jscpd)를 후속으로 검토한다.
- **Reviewer:** 기준표(6.3)에 중복 항목을 포함한다.

### 6.3 낮은 품질 방지 **[확정]**

- **품질 검사 명령:** 포맷·린트·타입 검사·빌드를 Phase 0에서 언어에 맞게 세팅하고 필수 검사로 등록한다. 기존 프로젝트에 이미 있는 위반은 6.5에 따라 처리한다.
- **프로젝트 규칙 문서:** Phase 0에서 작성하고 사용자가 승인한다. 기획서·기존 설정·기존 코드에서 확인한 규칙과 추정한 규칙을 구분해 적는다. Developer와 Reviewer에게 항상 입력으로 제공하며, 바꾸려면 사용자 승인이 필요하다. 위치는 `Phase/ProjectRules.md`이며 영문과 국문을 모두 쓴다.
- **Reviewer 기준표:**

| 항목 | 확인 내용 |
|---|---|
| 요구사항 | 승인된 요구사항과 완료 기준을 충족하는가 |
| 테스트 | 의미 있는 테스트인가, 경계·오류 경우를 다루는가, 삭제·약화가 있는가 |
| 중복 | 기존 기능을 재구현하거나 복사해 붙여넣지 않았는가 |
| 구조 | 프로젝트 규칙과 기존 구조를 따르는가, 책임이 적절히 나뉘었는가 |
| 가독성 | 이름, 복잡도, 불필요한 코드 |
| 오류 처리·보안 | 입력 검증, 비밀값 노출, 위험한 동작 |
| 범위 | 승인 범위 밖의 변경이 있는가 |
| 기준 완화 | 계획에 없는 설정 변경, 새 검사 회피 주석, 잠금 파일의 기존 버전 변경이 있는가 (4.2, 6.4) |

- 지적마다 중요도와 필수 여부를 붙인다. 필수 지적이 남아 있으면 Task를 완료할 수 없다.
- **필수가 될 수 있는 항목:** 요구사항, 테스트, 중복, 오류 처리·보안, 범위, 기준 완화. 구조와 가독성은 기본적으로 권고이고, 프로젝트 규칙 문서를 어긴 경우에만 필수가 된다. AI의 취향이 아니라 사용자가 승인한 규칙으로 막기 위해서다. 권고 지적은 보고서에 보여주지만, 고치지 않아도 Task를 끝낼 수 있다.
- 지적별 처리 결과(수정 확인, 오탐, 보류)를 기록한다. 리뷰가 실제로 품질을 높였는지 판단하는 근거가 된다.

### 6.4 기준 완화 차단 **[확정]**

- 린트 규칙 끄기, 테스트 제외, 검사 대상 축소, 임계값 낮추기 같은 품질 기준 완화는 범위 변경으로 본다. 사용자 승인 없이는 적용하지 않는다.
- Phase 0에서 검사 설정 파일 목록(예: ESLint 설정, `tsconfig.json`, Python 린트 설정, Java Checkstyle 설정)을 함께 등록하고 사용자가 승인한다. 하네스는 언어를 모르므로 어떤 파일이 검사 설정인지 스스로 알 수 없기 때문이다.
- 검사 명령의 변경은 항상 사용자 승인을 받는다.
- **설정 파일 변경 [확정: H2]:** 정상적인 개발 중 질문이 지나치게 많아지지 않게 하면서, 완화는 막기 위해 아래처럼 처리한다.

| 경우 | 처리 |
|---|---|
| 계획에 적힌 설정 변경 (예: 새 소스 폴더를 검사 대상에 추가) | "시작" 승인에 포함한다. 따로 묻지 않는다 |
| 계획에 없는 설정 변경 | 하네스가 변경을 표시하고, Reviewer가 완화인지 아닌지 반드시 분류한다. 완화이면 멈추고 사용자 승인을 받는다. 완화가 아니면 계속 진행한다 |
| 모든 설정 변경 | 결과 보고서에 따로 모아 보여주고, 사용자가 인수할 때 확인한다 |

- 하네스는 언어를 모르므로 설정 변경이 완화인지 스스로 구분하지 못한다. 그래서 Reviewer가 분류하고, 인수 때 사용자가 확인하는 두 단계로 둔다. Reviewer가 분류를 잘못해도 마지막에 사람이 보게 하기 위해서다.
- `pyproject.toml`, `package.json`처럼 검사 설정과 라이브러리 목록이 한 파일에 있어도 같은 규칙을 따른다. 라이브러리 추가 자체는 7.1의 의존성 규칙을 따른다.
- **검사 회피 주석 [확정: H2]:** 설정 파일을 바꾸지 않고 코드 안의 주석으로 검사를 피할 수도 있다(예: `eslint-disable`, `# noqa`, `# type: ignore`, `@ts-ignore`, `@SuppressWarnings`). Phase 0에서 프로젝트 언어에 맞는 주석 패턴을 등록한다. 하네스는 이 패턴을 글자 그대로 찾아 기준선보다 새로 생긴 것을 보고한다. Reviewer는 반드시 확인하고, 정당한 사유가 없으면 필수 지적으로 낸다. 사유가 있으면 그 사유와 함께 보고서에 표시해 사용자가 인수할 때 확인한다.
- 리뷰는 AI의 판단이므로 품질을 보장하지 않는다. 자동 검사와 사용자 인수를 함께 유지한다.

### 6.5 새로 생긴 문제만 막는다 **[확정]**

기존 프로젝트에 이미 있는 중복이나 품질 문제 때문에 개발을 시작하지 못하는 일이 없도록 한다. Phase 0에서 기록한 기준선보다 나빠진 부분만 막는다.

| 대상 | 처리 |
|---|---|
| 중복 | 내장 탐지기가 기준선과 비교해 새로 생긴 중복만 보고한다 |
| 검사 회피 주석 | 기준선과 비교해 새로 생긴 주석만 보고한다 (6.4) |
| 품질 검사 위반 | Phase 0에서 기존 위반을 (a) 고치거나, (b) 도구의 기준선·예외 목록 기능에 등록하거나, (c) 검사 범위를 정해서, 시작 시점에 통과하는 상태를 만든다. 이후에는 종료 코드로 판정한다 |
| 예외 목록 | Phase 0 이후 예외 목록에 항목을 추가하는 것은 기준 완화로 보고 사용자 승인을 받는다 (6.4) |
| 테스트 **[확정]** | 실패하는 테스트는 기준선으로 허용하지 않는다. 기존 실패는 Phase 0에서 고치거나 사용자가 직접 고친 뒤 시작한다. 실패를 안고 시작하면 새 변경이 무엇을 망가뜨렸는지 가려낼 수 없기 때문이다 |

## 7. 개발 실행

```text
Task 범위·선행 조건 확인
→ Developer: 기존 코드 탐색, 구현, 테스트 작성
→ 하네스: 테스트·품질·중복 검사 실행
→ 통과하면 Reviewer: 기준표로 리뷰
→ 필수 지적이 있으면 Developer 수정 → 재검사·재리뷰
→ Task 기술적 완료
```

### 7.1 AI 권한 **[확정]**

| 동작 | 처리 |
|---|---|
| 프로젝트 읽기·검색 | AI가 직접 한다 (읽기 전용). 비밀값 파일은 제외한다 (아래) |
| 파일 생성·수정·삭제·이름 변경 | 계획에 적힌 파일과 폴더 안에서는 AI가 변경안을 제출하면 하네스가 기준 해시를 확인한 뒤 적용한다. 그 폴더 안에 새 파일을 만드는 것도 포함한다. 그 밖의 기존 파일을 고치거나 계획에 없는 폴더에 새 파일을 만들려면 멈추고 사용자 승인을 받는다 |
| 등록된 검사 명령 | Developer가 작업 중 요청하면 하네스가 실행해 결과를 돌려준다. Task당 기본 5회이며 설정으로 바꿀 수 있다. Reviewer 지적 후 수정 한도(7.2)와는 별개다 |
| 계획에 명시된 의존성 추가 | Phase 계획 승인으로 허용한다. 실행은 하네스가 한다 |
| 계획에 없는 설치, 외부 네트워크, 시스템 변경 | 실행 전에 사용자 승인을 받는다 |
| 관리자 권한 작업 | 하네스가 실행하지 않는다. 사용자가 수동으로 처리한다 |
| Git 쓰기·배포 | 하지 않는다. 사용자가 수동으로 한다 **[확정]** |
| 버전 변경 | 주요 구성(런타임, 프레임워크, DB)은 하지 않고 사용자가 직접 한다. 일반 라이브러리는 충돌 시 이유와 대안을 제시하고, 사용자 승인을 받아 하네스가 실행한다 **[확정]** (4.2) |
| 하네스 정책·승인 기록·등록된 검사 명령 변경 | 금지한다. 검사 명령은 사용자 승인으로만 바꾼다. 검사 설정 파일의 변경은 6.4를 따른다 |

**비밀값 파일 제외 [확정]:** AI가 읽은 내용은 외부 AI 서비스로 전송된다. 그래서 다음 파일은 AI가 읽지도 고치지도 못하게 한다: `.env`(`.env.`으로 시작하는 파일 포함), `*.key`, `*.pem`, `credentials`, `secrets` 폴더. 제외된 파일을 고쳐야 하는 작업이 생기면 AI는 멈추고 사용자에게 알린다.

첫 버전은 AI가 요청하고 하네스가 실행하는 방식(중개)으로 한다 **[확정: Q2 (가)]**. AI가 직접 실행하는 방식은 관리자 권한 없는 Windows에서 권한 경계를 검증한 뒤 검토한다.

### 7.2 수정 한도와 중단 (0.4 유지)

- 자동 수정 한도는 설정할 수 있고 기본값은 2회다. 실사용 기록을 보고 조정한다.
- 한도를 넘으면 원인, 시도 내역, 남은 결과를 보고하고 중단한다.
- 환경 문제는 코드 수정으로 재시도하지 않는다.

### 7.3 Phase 통합 검증 (0.4 유지)

모든 Task가 끝나면 최종 코드에서 등록된 검사 전체를 다시 실행한다. Task 단계의 통과 결과를 재사용하지 않는다.

## 8. 산출물 안내와 인수

### 8.1 산출물 안내 보고서 **[확정]**

사람이 읽는 1–2페이지 Markdown으로 만들고, 상세 기록은 링크로 연결한다. 위치는 `Phase/Reports/PhaseN_Report.md`로 한다. 실패한 경우에도 보고서는 생성한다. 보고서도 Phase 문서와 같이 영문과 국문을 모두 쓴다 **[확정]**.

| 항목 | 내용 |
|---|---|
| 개발 결과 | 구현한 기능, 변경 파일, 실행 방법 |
| 검증 결과 | 테스트 수와 통과 여부, 품질 검사, 새로 생긴 중복(그대로 복사한 코드만 탐지), 격리 수준 |
| 설정·버전 변경 | 검사 설정 파일 변경과 Reviewer의 분류, 새 검사 회피 주석과 사유, 잠금 파일 변경 |
| 리뷰 결과 | 지적 수, 처리 결과, 남은 지적 |
| 재사용 항목 | 확인 방법과 결과 |
| 사용자 확인 항목 | UI 등 직접 확인할 순서와 기대 결과 |
| 남은 문제·제한 | 미검증 항목, 예외 |
| 실행 요약 | 역할별 AI 호출 수, 소요 시간, 승인 대기 시간 |

### 8.2 인수 **[확정]**

- 사용자가 OK하면 인수를 기록하고, Phase 문서를 완료 처리한 뒤(3.4), 다음 Phase 상세 계획을 제시한다.
- 필수 조건(검사, 필수 지적, 재사용 확인, 수동 확인)이 충족되지 않으면 인수할 수 없다. 사용자 OK만으로 완료 처리하지 않는다. 일부 범위를 빼려면 계획을 변경해 승인받는다.
- 수정 요청은 두 경로로 처리한다(0.4 유지).
  - 승인된 요구사항대로 동작하지 않으면 같은 Phase에서 수정·재검증한다.
  - 기능이나 범위를 바꾸려면 계획을 수정해 승인받은 뒤 구현한다.

## 9. 상태·기록·재개 (0.4 유지)

- 실행 상태, 승인, 검사 근거는 SQLite에 저장한다. 실행 DB와 로그는 OneDrive 밖에 둔다.
- 코드 버전은 Git 없이 파일 내용 해시로 식별한다. 사용자 변경을 보존하고, 기록과 실제 파일이 다르면 차이를 보여주고 중단한다.
- 같은 프로젝트는 한 번에 하나의 실행만 진행한다.
- 중단 후 기록된 단계부터 재개한다. 재개할 때 AI 호출이 중복되지 않게 한다.
- 실행 기록: 역할·목적별 AI 호출 수, 단계별 소요 시간, 승인 대기 시간, 리뷰 지적과 처리 결과.

## 10. 범위

### 10.1 첫 버전에 포함

- 기획서 기반 Phase 구성과 Phase 문서 생성·완료 처리
- Phase 0 환경 세팅 (승인된 명령 실행, 관리자 권한 작업은 수동 안내)
- 언어와 무관한 검사 계약
- 6장 품질 장치 (탐색, 중복 탐지(그대로 복사한 코드, 보조 수단), 품질 검사, 프로젝트 규칙, Reviewer 기준표, 기준 완화 차단, 검사 회피 주석 추적)
- Task 순차 실행, 제한된 수정, 통합 검증
- 산출물 안내 보고서, 인수, 수정 요청 두 경로
- 상태 기록, 재개, 동시 실행 방지, 사용자 변경 보존

### 10.2 제외

- Git 쓰기와 배포 **[확정]**
- 주요 구성(런타임, 프레임워크, DB)의 버전 변경. 필요하면 사용자가 직접 한다 **[확정]**. 일반 라이브러리의 충돌 해결은 4.2에 따라 승인 후 하네스가 실행한다
- 이름만 바꾼 복사나 비슷한 로직의 중복 탐지. 첫 버전은 그대로 복사한 코드만 찾는다 **[확정]**
- UI 자동 테스트. 사용자가 직접 확인한다
- 관리자 권한 작업의 자동화
- 병렬 Task, 여러 AI 도구 동시 사용, 웹 대시보드
- 사용자 변경 자동 병합, 충돌 자동 복구
- Phase 없는 작은 수정 요청 (다음 버전 후보)
- Fast·Standard·Strict 분기 (실사용 기록을 보고 판단)

### 10.3 실행 환경 조건

- **하네스 실행 환경:** Windows, 관리자 권한 없이 동작한다 **[확정: 회사 정책]**.
- **AI 실행 도구 [확정: I1]:** 첫 버전은 Codex CLI 하나다. 이것은 구현상의 선택이며 대상 프로젝트의 언어 제약이 아니다. Claude Code는 Codex 다음에 개발한다.
  - **첫 버전:** AI 연결 부분을 도구와 상관없는 공통 틀과 Codex 모듈로 나눈다(12장 5단계). 예시가 Codex 하나뿐이면 공통 틀이 Codex에 맞춰지기 쉬우므로, 공통 틀을 정할 때 Claude Code가 그 틀에 맞는지 작게 시험한다. 확인할 것은 명령줄에서 요청 하나를 보내고 답을 받을 수 있는지, AI의 도구를 끄거나 읽기 전용으로 제한할 수 있고 실제로 막히는지, 결과를 정해진 형식으로 받을 수 있는지, 회사 환경에서 관리자 권한 없이 로그인하고 실행되는지다. 완성이 아니라 확인만 한다. 회사에서 Claude Code 로그인을 쓸 수 없으면 문서로만 확인하고 한계로 기록한다.
  - **첫 버전 인수 후:** Claude Code 모듈을 개발한다. Codex와 같은 안전 확인(허락된 동작만 할 수 있는지 실제로 검증)을 거치고, Planner·Developer·Reviewer를 Claude Code로 바꿔도 같은 판정이 나오는지 확인한다.
  - **그다음:** 두 도구를 함께 쓰는 방식(예: Developer는 Codex, Reviewer는 Claude Code)을 검토한다. 서로 다른 AI가 리뷰하면 같은 AI라서 같은 실수를 놓치는 문제를 줄일 수 있다. 첫 버전에서는 여러 AI 도구 동시 사용을 제외한다 (10.2).
- **대상 프로젝트:** 언어 제한은 없다. 다만 Windows에서 일반 사용자 권한으로 설치·실행할 수 있어야 하고, 표준 테스트 보고서를 출력할 수 있어야 한다(출력할 수 없으면 5장 예외 절차를 따른다).
- **DB [확정]:** 첫 버전은 SQLite로만 검증한다. 현재 회사 환경에서 사용할 수 있는 DB가 SQLite뿐이기 때문이다. MSSQL·PostgreSQL 같은 DB 서버는 "미지원"이 아니라 "미검증" 한계로 남긴다. 하네스에는 DB별 코드가 없으므로, 검증되지 않은 부분은 다음 세 가지다.
  - DB 서버 설치: 관리자 권한이 필요할 가능성이 높아 사용자가 수동으로 준비하는 경로를 쓴다.
  - 로컬 네트워크 접속: AppContainer 격리 안에서는 막히므로 방식 B로 실행한다 (5.1).
  - 테스트용 DB 분리와 정리: 서버 DB에서는 테스트마다 별도 DB나 스키마를 쓰는 방법을 정해야 한다.
- **DB 접속 정보 [확정]:** 나중에 DB 서버를 쓰게 될 때를 대비해, 접속 정보는 사용자가 준비해 환경 변수로 제공한다. 비밀번호는 기획서·계획·AI 입력에 넣지 않는다.

## 11. 현재 구현과의 관계 **[확정]**

지금 저장소에서 이어서 수정한다(F1). 새로 만드는 부분보다 그대로 쓰는 부분이 많고, 기존 회귀 검사가 수정 중에 망가진 곳을 잡아주기 때문이다. 자기 개발을 하지 않으므로, 개발은 기존 AI 코딩 도구(Claude Code, Codex)로 한다.

| 영역 | 현재 구현 | 처리 |
|---|---|---|
| 상태·기록·재개 (`store`, `files`, `processes`, `workflow_records`, `workflow_recovery`) | 언어와 무관 | 재사용 |
| 승인 버전 고정·인수 조건 (`workflow`, `workflow_acceptance`) | 언어와 무관. 계획 승인과 실행 승인이 분리됨 | 재사용. 계획 승인과 실행 지시를 "시작" 하나로 합침 |
| 피드백 두 경로 (`workflow_feedback`) | 언어와 무관 | 재사용 |
| 계획 생성 (`codex_adapter`, `planning`, `plan_schema`) | Phase 0 개념 없음. 지정한 파일만 입력 | 확장: Phase 0, 세팅 명령, 검사 계약, 프로젝트 규칙 |
| 검사 실행 (`validation`, `isolated_validation`, `windows_appcontainer`) | Python·pytest 전용 | 재설계: 5장 검사 계약. Python은 기존 AppContainer 격리를 유지하고, 그 밖의 경우는 방식 B로 실행 (5.1) |
| AI 권한 (`workers`, `worker_contract`) | 텍스트만 반환. 지정 파일만 읽음. 삭제·이름 변경 불가. 의존성 변경 금지 | 재설계: 7.1 |
| Reviewer 지침 (`workers`) | 요구사항, 범위, 테스트 약화 | 확장: 6.3 기준표 |
| 결과 보고 (`results`) | JSON만 | 확장: 8.1 보고서 |

## 12. 개발 순서 **[확정]**

위험이 큰 항목(Java 다운로드, 격리 방식)부터 먼저 확인하는 순서다. 하네스 자체의 개발 Phase는 이 단계를 아래처럼 묶는다 (14.1 G1). 문서는 [`Phase/Overview.md`](../Phase/Overview.md)에 있다.

- Phase 0 기준선 확인: 현재 저장소의 환경과 회귀 검사를 확인하고 기준선을 기록한다. 4.4의 "확인만" 형태를 하네스 자신에게 적용한 것이다.
- Phase 1 검사 계약과 격리: 1–2단계
- Phase 2 계획 확장과 환경 세팅: 3–4단계
- Phase 3 개발 흐름과 품질 장치: 5–6단계
- Phase 4 실사용 검증: 7단계

**Phase 1 예제 범위 (2026-10-23 확정·구체화):** 공통 검사 계약·격리·변조 탐지·워크플로와 인수 연결의 개발 범위는 유지한다. Python과 Java 예제는 작은 함수, 소수의 테스트, 실행·보고서 출력에 필요한 설정과 의존성을 가진 검증용 프로젝트 각 1개로 제한한다. 같은 예제를 환경 확인과 검사 검증에서 재사용하고, 통과·실패·미실행·시간 초과·테스트 삭제·새 skip 등을 통제된 변형으로 확인한다. Java 빌드 도구는 하나를 선택한다. 화면·웹 서비스·DB·인증·업무 기능을 추가하지 않으며, 필요한 프로세스·네트워크·변조 확인만 일회용 로컬 보조 프로그램으로 수행한다. 필수 검증과 전체 회귀 검사는 유지하고 실제 프로젝트 개발 검증은 13.1의 Phase 4에서 수행한다.

| 단계 | 목표 | 확인할 결과 |
|---|---|---|
| 1 | 검사 계약 | 언어와 무관한 명령 실행, JUnit 판정, 테스트 목록 비교. Python과 Java 예제로 확인하며, 이때 Java 패키지 다운로드(Maven·Gradle)가 회사 네트워크에서 되는지도 확인 |
| 2 | 격리 방식 C | 기존 AppContainer 경로 유지, 방식 B와 변조 탐지 구현, 보고서에 격리 수준 표시 |
| 3 | 계획 확장과 Phase 문서 | Phase 0을 포함한 계획, `Phase/` 문서 생성 |
| 4 | Phase 0 환경 세팅 | 승인된 명령 실행, 수동 단계 안내 후 재개, 검사 계약 충족 확인 |
| 5 | AI 권한과 품질 장치 | 읽기 탐색, 삭제·이름 변경, 검사 요청, 중복·품질 검사, Reviewer 기준표, 기준 완화 차단 |
| 6 | 산출물 안내와 인수 | 보고서, 인수 시 문서 완료 처리, CLI 단순화 |
| 7 | 실사용 검증 | 13.1 예제로 13장 완료 기준 확인 |

## 13. 첫 버전 완료 기준

- [ ] 기획서만 주면 Phase 0을 포함한 Phase 구성과 Phase 문서가 생성된다.
- [ ] 기획서에 기술 구성이 없으면 제안하고 사용자 확인을 거친다.
- [ ] 사용자가 시작을 지시하기 전에는 세팅이나 구현을 하지 않는다.
- [ ] Phase 0에서 승인된 명령으로 환경을 세팅한다. 관리자 권한이 필요한 작업은 수동 절차를 안내하고 처리 후 재개한다.
- [ ] 세팅이 필요 없는 프로젝트에서는 Phase 0이 확인만으로 짧게 끝나고 기준선을 기록한다.
- [ ] Phase 0과 개발 Phase를 각각 따로 시작하고 인수한다.
- [ ] **Python·TypeScript·Java 예제에서 하네스 코드를 고치지 않고 동작한다.** 이 중 하나는 SQLite DB를 사용하고, 신규 프로젝트와 기존 프로젝트를 각각 하나 이상 포함한다 (13.1).
- [ ] 테스트 미실행, 테스트 0개, 실패, 테스트 삭제를 통과로 표시하지 않는다.
- [ ] 품질 검사와 중복 검사 결과가 리뷰와 보고서에 반영된다. 중복 탐지의 정확도는 기준이 아니다.
- [ ] 기존 중복·품질 위반은 막지 않고, 기준선보다 새로 생긴 문제만 막는다.
- [ ] Reviewer가 별도 세션에서 기준표로 리뷰하고, 필수 지적의 처리 근거를 남긴다.
- [ ] 품질 기준 완화는 사용자 승인 없이 적용되지 않는다. 계획에 없는 설정 변경과 새 검사 회피 주석은 Reviewer가 확인하고 보고서에 모두 표시된다.
- [ ] 버전은 사용자 승인 없이 바뀌지 않고, 주요 구성의 버전은 하네스가 바꾸지 않는다.
- [ ] 산출물 안내 보고서가 실패한 경우를 포함해 항상 생성된다.
- [ ] 인수하면 Phase 문서가 완료 처리되고, 필수 조건이 충족되지 않으면 인수가 막힌다.
- [ ] 중단 후 재개, 동시 실행 방지, 사용자 변경 보존이 동작한다.
- [ ] 검사 중 실행된 코드가 하네스 기록을 바꾸면 차단되거나, 탐지되어 중단된다.
- [ ] Git 쓰기와 배포를 하지 않는다.
