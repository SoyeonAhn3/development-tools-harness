## 1. 이 문서의 목적

v0.1(2026-09-11)과 MVP v0.4(2026-09-14)는 12개 설계 축 중 11개가 서로 반대였고, 뒤집힌 근거가 어디에도 기록되지 않았다. 이 문서는 각 축의 최종 결정과 근거를 한 곳에 고정한다.

앞으로 하네스의 설계 변경은 이 표에 행을 추가하는 방식으로 관리한다.

### 3.4 Git 쓰기 정책 상세 (D-12)

사용자 결정: 자동 커밋하되, 사용자가 개발 사항을 승인했을 때 진행한다.

| 동작 | 조건 |
|---|---|
| 하네스가 쓰는 대상 | `harness/phase/<phase-id>` 전용 브랜치 **한정** |
| main·기존 브랜치 직접 커밋 | **금지** |
| 브랜치 생성 | 해당 Phase 계획에 유효한 승인이 있을 때만 |
| Task 커밋 | 승인된 계획 범위 안의 Task에 한해, 검증 통과 후 자동 |
| 승인이 없거나 무효화된 상태 | 커밋하지 않고 승인 대기로 정지 |
| push / merge / main 반영 | 별도 승인 |
| Phase 완료 처리 | 커밋이 있어도 사용자 결과 승인 전에는 완료로 처리하지 않음 |

승인과 커밋의 관계는 다음과 같다. 커밋은 작업의 저장이고, 완료는 사용자의 인수다. 둘을 같은 것으로 취급하지 않는다.

### 3.7 데이터 모델 (상세는 `data-model-spec.md`)

| ID | 결정 항목 | 확정 | 근거 |
|---|---|---|---|
| D-24 | 상태 구조 | **굵은 상태 + `current_step` 컬럼 분리** | 단계를 상태 이름에 녹이면 Workflow별로 상태 집합이 달라져 전이표가 3벌 필요해진다. Workflow가 단계 순서를 정의하고 상태 머신은 1벌만 유지한다 |
| D-25 | Run 단위 | **Phase 실행만 Run으로 관리** | 계획 수립과 기획 검토는 파일 산출물이라 중단 시 재실행하면 된다. `resume` 대상이 하나여야 모호하지 않다 |
| D-26 | 이력 저장 | **도메인별 이력 테이블** (approvals / rejections / task_attempts / validations / reviews) | 조회 패턴이 status·report·resume로 정해져 있다. 범용 이벤트 로그의 JSON payload는 제약 검증이 약하다. 완전한 Event Sourcing은 MVP 제외 방침과도 일치 |
| D-27 | 코드 Revision | **Git 임시 index tree hash** (`GIT_INDEX_FILE` + `write-tree`) | `.gitignore`를 그대로 따라 제외 규칙을 재구현하지 않는다. 새 파일·삭제·권한 변경이 반영되고 사용자 스테이징 영역을 건드리지 않는다 |
| D-28 | 프로젝트 식별자 | **`{project.id}-{repo-path-hash}` 디렉토리** | 같은 이름의 다른 체크아웃을 구분하면서 사람이 읽을 수 있다 |
| D-29 | 승인 연결 범위 | **`plan_hash`(Phase) + `task_hash`(Task) 2계층** | 전역 hash 하나면 무관한 Task 추가로 모든 승인이 무효화된다. 반려 후 무효화 범위를 Task 단위로 좁히려면 Task hash가 필요하다 |
| D-30 | 동시 실행 제어 | **`runs.owner_pid` + heartbeat** | 파일 락은 OneDrive 동기화 폴더에서 신뢰하기 어렵다. DB는 LocalAppData에 있어 안전하다 |
| D-31 | 검증 로그 | **요약·종료 코드는 DB, 전체 로그는 파일 + 경로만 DB** | 테스트 로그는 수 MB가 되어 DB가 비대해진다 |
| D-32 | 스키마 버전 | **`schema_meta`에 기록, 불일치 시 중단·안내** | 자동 마이그레이션은 검증 비용이 커서 v1.1로 미룬다 |
| D-33 | 백업 | **Task 완료·정상 중단 시 최근 10개 순환** | MVP 5.3의 백업 규정에 보관 개수가 없었다 |

추가로 다음 설계 원칙을 확정한다.

- 파생값을 중복 저장하지 않는다. `validated_revision`·`reviewed_revision`은 검사 이력에서 계산하며 `tasks`에 사본을 두지 않는다.
- `plan_hash` 계산에서 `plan.md`의 서술 문장은 제외한다. 설명 문구 수정만으로 승인이 무효화되지 않게 한다.
