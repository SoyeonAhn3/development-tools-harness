# Development Harness v0.1 개발 계획

작성일: 2026-09-11\
문서 상태: 개발 방향 합의 / 첫 버전 범위·승인 정책은 확정 제안 / 구현 미착수

## 1. 이 문서의 목적과 결정 상태

여러 프로젝트에서 재사용할 수 있는 AI 에이전트 기반 반자동 개발 하네스의 구조, 첫 버전 범위, 사용자 승인 시점과 완료 기준을 정리한다.

Decision Desk의 제품 기획과 개발 하네스의 기획은 구분한다. Decision Desk의 업무 규칙은 [Decision Desk 기획 문서](./decision-desk-기획문서.md)를 원본으로 유지하며 이 문서에 중복 정의하지 않는다.

| 구분 | 상태 |
|---|---|
| Decision Desk 첫 실사용 버전의 필수 제품 기획 | 완료. 실제 기술·실행 환경 검증은 개발 중 수행 |
| 중요한 사항은 사용자가 검토하는 반자동 개발 | 사용자 지향점 |
| 공통 Harness와 프로젝트별 Profile 분리 | 사용자 제안 및 후속 설계 방향에 동의 |
| 작은 하네스부터 개발 | 사용자 동의 |
| 아래 v0.1 상세 범위와 승인 정책 | 확정 제안. 문서 작성 요청 자체를 상세 정책의 일괄 승인으로 취급하지 않음 |
| 하네스 구현·패키지 설치·Git 변경·외부 연동 | 이 문서 작성으로 수행하지 않음 |

이후 하네스 관련 결정과 변경은 이 문서에서 이어서 관리한다. 아직 채택하지 않은 추천을 사용자 확정 사항으로 표시하지 않는다.

## 2. 목표

> 기능 하나를 맡기면 AI가 계획 → 구현 → 독립 검토 → 검증을 진행하고, 중요한 지점에서 사용자 승인을 기다리는 개발 실행기를 만든다.

- 승인된 범위 안의 반복 작업은 자동으로 진행한다.
- 사용자는 중요한 설계, 범위 변경, 위험한 동작, 기능 결과를 검토한다.
- 진행 상태와 검증 근거를 기록해 중단 후에도 이어갈 수 있게 한다.
- 프로젝트의 도메인 지식과 검증 방법은 Profile로 분리한다.
- 첫 적용 사례는 Decision Desk로 삼고, 작은 별도 예제 프로젝트로 재사용성을 확인한다.

목표는 모든 명령에 대해 Enter를 반복해서 누르는 개발이 아니라, 판단이 필요한 순간에 근거를 보고 승인하는 개발이다.

### 목표로 하지 않는 것

- 사람의 판단이 전혀 필요 없는 완전 자율 개발
- 에이전트의 완료 선언만으로 요구사항 충족을 보장하는 것
- 모든 미래 프로젝트를 설정 변경만으로 반드시 처리한다고 보장하는 것
- 회사 정책이나 실행 환경의 권한 제한을 하네스 설정으로 우회하는 것

새로운 도구가 필요하면 Adapter나 검증 기능을 확장할 수 있다. 그때도 공통 실행 흐름을 프로젝트별로 다시 작성하지 않는 구조를 지향한다.

## 3. 공통 구조

| 구성 | 책임 | 변경 단위 |
|---|---|---|
| Harness Core | 실행 순서, 선행 조건, 재시도, 승인 대기, 완료 판정 | 공통으로 재사용 |
| Project Profile | 기획·설계 문서 참조, 업무 규칙, 작업 목록, 검증 명령, 승인 정책 | 프로젝트별 관리 |
| Runtime Adapter | 실제 AI 실행 도구 호출, 명령 실행과 결과 수신 | 실행 도구별 교체·확장 |
| Run State / Evidence | 현재 단계, 변경 내역, 검토·검증 결과, 승인 기록 | 실행별 생성·보존 |

프로젝트를 바꾸는 것과 AI 실행 도구를 바꾸는 것을 분리한다.

- Decision Desk: 공통 Harness + Decision Desk Profile
- AI Analytics: 공통 Harness + AI Analytics Profile

Core에 평가 기준, 평가자, 점수 계산 같은 Decision Desk 업무 로직을 넣지 않는다. Profile에는 기존 기획 문서의 위치와 관련 항목을 참조하고, 같은 규칙을 여러 문서에 다시 작성하지 않는다.

## 4. 첫 버전 범위 — v0.1 제안

### 4-1. 포함

| 항목 | v0.1 범위 |
|---|---|
| 실행 환경 | Windows PC의 터미널에서 실행하는 로컬 CLI |
| 프로젝트 설정 | JSON 설정과 Markdown 문서를 읽고 필수 항목·문서 경로·작업 경계를 확인 |
| Work Item | 작업 ID, 범위, 관련 기획, 인수 조건, 선행 작업 관리 |
| 계층 | Phase·Feature·Ticket 계층을 강제하지 않음. 상위 관계는 선택 사항 |
| 역할 | Planner, Developer, Reviewer, Tester를 별도 세션으로 순차 실행 |
| Workflow | 순차 단계 구성을 설정으로 관리. 필수 검증·승인은 임의 생략 불가 |
| 수정 작업 | 한 번에 실행 작업 하나, 제품 코드 수정 에이전트도 하나 |
| 검증 | Profile에 정의한 필수 검증 명령 실행, 성공 조건 확인, 로그 수집 |
| 수정 반복 | 검토·검증 실패에 대해 최대 3회 자동 수정 후 중단·보고 |
| 승인 | 계획 승인, 결과 승인, 예외 발생 시 추가 승인 |
| 진행 관리 | 현재 단계·승인 대기·실패 이유 조회, 실행 기록 저장, 단계 단위 재개 |
| 결과 보고 | 변경 요약, 변경 파일, 검토 결과, 검증 결과, 미검증 사항, 사용자 확인 항목 |
| Git | 상태와 변경 차이 조회만 지원. 쓰기 동작은 자동화하지 않음 |
| 재사용성 확인 | Decision Desk용 Profile과 작은 별도 예제 Profile로 검증 |

### 4-2. 제외

- 병렬 개발, 자동 작업 분배, 복잡한 분기·합류 Workflow
- 웹 대시보드와 자체 채팅 화면
- 여러 AI 실행 도구 동시 지원
- 많은 전문 에이전트의 초기 도입
- 자동 branch 생성·commit·push·PR 생성·merge·배포
- 운영 DB 변경과 실데이터 처리 자동화
- 패키지 설치·외부 연동을 위한 범용 자동 실행 승인 시스템
- 에이전트 실행 중 모든 내부 권한 팝업을 자체 화면으로 통합하는 기능

v0.1의 완료는 사용자가 검증된 변경을 받아들였다는 뜻이다. 커밋, PR, 병합이나 배포 완료와 동일하게 취급하지 않는다.

## 5. Project Profile과 Work Item

### 5-1. Profile에 담을 것

- 프로젝트 식별자와 명시적인 작업 루트
- README, 제품 기획, Architecture, Domain Rules의 위치
- Work Item 목록과 문서 참조
- 사용할 역할과 순차 Workflow
- 검증 명령, 실행 위치, 필수 여부, 성공 조건, 제한 시간, 결과물 위치
- 프로젝트 공통 Definition of Done
- 승인 정책, 허용 작업 범위와 금지 대상
- 재시도·시간 제한, 실행 기록 보관 위치
- Profile 형식 버전

실행에 사용한 설정 버전을 기록한다. 프로젝트 설정은 회사·실행 환경의 제한을 완화할 수 없으며, 작업 에이전트가 자신의 승인 정책을 수정해 권한을 넓히는 것도 허용하지 않는다.

### 5-2. Work Item의 공통 정보

아래는 개념 필드이며 최종 파일 스키마는 구현 설계에서 정한다.

| 정보 | 설명 |
|---|---|
| id | P1-F1, AUTH-F1, PAYMENT-003처럼 프로젝트가 정하는 식별자. ID 문자열로 계층을 추측하지 않음 |
| type | phase, feature, ticket, bug, refactor, migration 등 분류 |
| parent | 선택적인 상위 항목 |
| depends_on | 먼저 완료해야 하는 작업 |
| scope | 해야 할 일과 하지 않을 일 |
| spec_refs | 관련 기획·업무 규칙의 원본 참조 |
| acceptance_criteria | 해당 요구사항의 충족을 확인할 조건 |
| risk | 사용자 검토가 필요한 위험 요소 |
| 실행 구분 | 실제 실행 작업인지, 하위 작업을 묶는 항목인지 구분 |

계층과 실행 의존성은 별개다. 묶음 항목 전체를 무조건 Developer에게 맡기지 않는다. v0.1에서는 실행 가능한 하위 작업과 선행 조건을 확인하고 순차적으로 처리한다.

작업 범위와 완료 조건이 불명확하거나 필수 선행 작업이 끝나지 않았다면 구현을 시작하지 않는다.

## 6. 역할과 실행 흐름

### 6-1. 역할별 책임

| 역할 | 책임 | 경계 |
|---|---|---|
| Planner | 기획과 Work Item을 읽고 구현·검증 계획 작성 | 제품 기획이나 작업 범위를 임의로 확정·변경하지 않음 |
| Developer | 승인된 범위의 코드·테스트 구현과 오류 수정 | 승인 정책·완료 기준을 바꿔 통과시키지 않음 |
| Reviewer | 기획, 인수 조건, 실제 코드·테스트 변경을 독립적으로 검토 | 개발자 설명만으로 판정하지 않으며 제품 코드를 직접 수정하지 않음 |
| Tester | 검증 사례와 실행 결과를 확인하고 미검증·실패 사항 보고 | 미실행을 통과로 표시하지 않으며 필요한 코드 수정은 Developer에게 반환 |
| Runner | 명령 실행, 종료 상태·로그 수집, 단계 전환, 승인·재시도 관리 | AI의 자연어 완료 선언만으로 다음 단계나 완료 상태로 이동하지 않음 |

역할 이름뿐 아니라 입력, 결과 형식, 허용 도구·경로, 시간 제한을 정의한다. Reviewer와 Tester는 해당 코드 버전과 기획을 독립적으로 확인한다. 같은 모델을 사용하더라도 세션을 분리하되, 역할 분리 자체가 검토의 정확성을 보장한다고 주장하지 않는다.

### 6-2. 기본 흐름

```text
프로젝트 설정·작업 루트·실행 환경 확인
    ↓
Work Item·관련 기획·선행 작업 확인
    ↓
구현·검증 계획 작성 또는 기존 승인 계획 확인
    ↓
① 사용자 계획 승인
    ↓
Developer 구현 + 빠른 자체 테스트
    ↓
Reviewer 독립 검토
    ↓
Tester 검증 + Runner의 검증 명령 실행
    ↓
실패·필수 지적 사항 → Developer 수정 → 필요한 검토·검증 재수행
    ↓
완료 조건과 증거 확인
    ↓
② 사용자 결과 승인
    ↓
해당 기능 완료
```

수정 반복 중 예외가 발생하면 해당 동작 전에 중단한다. 재시도 한도까지 실패하면 결과 승인 대기로 넘기지 않고 원인과 시도 내역을 보고한다.

검토한 코드, 테스트한 코드와 사용자에게 승인받는 코드는 같은 버전이어야 한다. 이후 수정이 생기면 영향을 받는 검토·검증·승인을 다시 수행한다.

## 7. 사용자 승인 정책 — 기본 2회 + 예외 승인

### 7-1. 최초 프로젝트 등록 확인

프로젝트를 처음 연결할 때 다음을 한 번 확인한다.

- 사용할 AI 실행 도구와 자료 전달 범위
- 작업 루트와 수정 가능한 범위
- 검증 명령과 실행 환경
- 공통 완료 조건과 승인 정책

이는 같은 설정으로 실행할 때마다 반복하는 승인이 아니다. 중요한 설정 변경 시에는 다시 확인한다.

### 7-2. 기능 시작 전: 계획 승인

사용자는 다음을 확인한다.

- 무엇을 만들고 무엇은 만들지 않는지
- 어떤 파일·구조를 바꿀 예정인지
- 완료 여부를 어떻게 검증할지
- 중요한 위험이나 새로운 의존성이 있는지

승인 단위는 내부 Ticket 하나하나가 아니라 사용자가 이해할 수 있는 기능 단위로 한다. 승인된 기능의 하위 작업은 계획 범위 안에서 자동 진행할 수 있다. 기존 승인 계획이 유효하다면 같은 내용을 다시 승인받지 않는다.

승인 전에는 해당 제품 코드의 구현을 시작하지 않는다. 계획·실행 기록 작성과 승인된 구현 범위를 구분한다.

### 7-3. 기능 완료 전: 결과 승인

다음 내용을 하나의 검토 자료로 제공한다.

- 변경 내용 요약과 변경 파일
- 실행 방법과 화면·동작 예시
- 자동 검증 결과 및 검토 지적 사항의 처리 결과
- 실행하지 못한 검증과 남은 위험
- 사용자가 직접 확인할 항목

자동 검증이 통과해도 사용자 승인 전에는 `결과 승인 대기`다. 수정 요청이 들어오면 관련 구현·검토·검증 단계로 돌아간다. 사용자가 결과를 받아들였을 때 해당 기능을 완료 처리한다.

### 7-4. 개발 중 추가 승인이 필요한 상황

| 상황 | 처리 |
|---|---|
| 기획·인수 조건·작업 범위 변경 | 이유와 영향을 제시하고 승인 대기 |
| 주요 구조·저장 방식 변경 | 대안과 영향을 제시하고 승인 대기 |
| 새 라이브러리 추가·설치 | 필요성과 변경 대상을 제시하고 승인 대기 |
| 승인된 AI 연결 외의 외부 API 사용·자료 전송 | 대상과 전송 내용을 제시하고 승인 대기 |
| 파일 대량 삭제·데이터 손실 가능성 | 동작 전에 중단하고 별도 확인 |
| 수정 한도 초과·실행 환경 문제 | 원인과 시도 내역을 보고하고 진행 방향 확인 |

승인한 범위 안의 파일 수정, 지정된 안전한 검증 명령, 통상적인 오류 수정은 매번 묻지 않는다. 다만 테스트라는 이름만으로 운영 DB나 외부 API 호출을 자동 허용하지 않는다.

### 7-5. 승인 공통 원칙

- 응답이 없으면 승인 대기를 유지한다. 무응답·시간 초과를 자동 승인으로 처리하지 않는다.
- 승인 대상 계획·설정·코드가 달라지면 기존 승인을 그대로 사용하지 않는다.
- 승인 기록에는 대상과 버전, 승인 여부를 연결한다. 구체적인 기록 방식은 기술 설계에서 정한다.
- 에이전트가 승인 기록을 작성·변조해 사용자 승인을 대체하지 못하게 한다.
- 승인 정책 변경이나 필수 검증 기준 완화는 일반 코드 수정과 구분해 검토한다.
- 하네스의 승인만으로 회사 정책·실행 도구 권한을 넓히지 않는다.

## 8. 업무 승인과 실행 권한의 분리

업무 승인은 “이 계획이나 결과를 받아들일 것인가”이고, 실행 권한은 “이 파일·명령·네트워크 동작을 기술적으로 허용할 것인가”다.

v0.1은 단계 사이에서 멈추고 사용자가 승인하면 재개하는 방식으로 시작한다. Codex 내부의 모든 권한 팝업을 자체 화면으로 통합하지 않는다.

- 업무 승인: Harness가 관리한다.
- 파일·명령·네트워크 권한: 실제 실행 환경이 제한한다.
- 권한 부족: 차단 이유를 기록하고 중단한다.
- 자동 권한 확대나 샌드박스 해제로 오류를 우회하지 않는다.
- 정책은 자동 허용·승인 요청·금지를 구분하되 실제 집행 가능한 범위만 지원한다.

Profile에 `ask`를 적는 것만으로 실행 차단이나 승인 팝업이 보장되는 것은 아니다. 실행 도구와 Runner가 해당 경계를 실제로 집행하는지 개발 초기에 확인해야 한다.

v0.1에서는 설치·외부 연동 같은 예외 작업을 승인받아도 지원하지 않는 작업까지 자동 실행하지 않는다. 필요한 환경 준비 후 상태를 재확인하고 재개한다. 자동으로 처리할 수 없는 동작은 수동 처리 대상으로 명시한다.

## 9. 검증과 Definition of Done

완료 판정은 다음 세 가지를 합쳐 수행한다.

1. 자동 검증: 테스트, 타입 검사, 린트, 빌드 등 프로젝트가 정의한 필수 검사
2. 요구사항 충족: 해당 Work Item의 인수 조건
3. 필요한 사람 검토: 화면, 사용 흐름과 중요한 판단

검증 명령 실행과 종료 코드·로그 수집은 Runner가 담당하고, 에이전트는 결과를 해석한다. 성공 조건은 명령마다 명시하며 명령이 실행됐다는 사실만으로 성공 판정을 내리지 않는다.

필수 검증의 실패, 미실행, 실행 환경 차단은 구분한다. 필수 검증을 실행하지 못하면 완료로 처리하지 않는다. 실패한 테스트를 삭제하거나 기준을 낮춰 통과시키는 변경은 별도 검토 대상이다.

프로젝트별 예시:

- Decision Desk: 저장 차단, 권한 검사, 오프라인 파일 실행, 종료·재실행, 백업·복원 등 제품 기획의 시나리오를 검증한다.
- AI Analytics: 데이터 검증, 고정된 평가 데이터와 기준값, 기존 결과 대비 회귀 여부 등을 Profile에서 정의할 수 있도록 한다.

위 예시는 프로젝트별 검증 책임을 설명하는 것이며, 하네스에 도메인별 계산 로직을 내장한다는 뜻이 아니다.

## 10. 실행 기록·중단·재개·수정 반복

### 저장할 기록

- 프로젝트·Work Item·실행 식별자
- 사용한 Profile·계획·코드 버전
- 현재 단계와 역할별 결과
- 변경 파일과 검토 지적 사항
- 검증 명령, 결과와 로그
- 승인 대상·승인 여부
- 수정 횟수, 실행 시간, 확인 가능한 사용량
- 중단 이유와 다음에 필요한 조치

단계 전환과 기록 저장은 Runner가 관리한다. 대화 내용에만 진행 상태를 남기지 않는다. 비밀값과 불필요한 실데이터를 기록·보고서에 포함하지 않도록 한다.

### 재개 원칙

- 정상 중지는 단계 경계를 기준으로 한다. 실행 중인 모델의 내부 상태를 임의 시점까지 완벽히 복원하는 기능을 약속하지 않는다.
- 비정상 종료 후에는 기록뿐 아니라 실제 파일·변경 상태를 확인한 뒤 재개한다.
- 작업 대상이나 코드가 바뀌었으면 이전 검증·승인의 유효성을 재확인한다.
- 사용자 수정과 관련 없는 기존 변경을 덮어쓰거나 자동으로 되돌리지 않는다.

### 수정 반복 원칙

- 최초 구현 이후 자동 수정은 최대 3회로 제한하는 것을 기본안으로 한다.
- 단계별 시간 제한을 설정하고 확인 가능한 사용량을 기록한다. 구체적인 기본값과 집행 방식은 개발 중 정한다.
- 권한 부족, 도구 미설치, 기획 모순을 코드 수정 반복으로 해결하려 하지 않는다.
- 승인 대기는 실패 횟수로 계산하지 않는다.
- 한도 초과 시 현재 결과, 실패 원인, 시도 내역과 필요한 판단을 보고한다.

## 11. 구현 방식과 프로젝트 위치 제안

### 기술 구성

- Node.js 기반 로컬 Runner
- 기존 Codex CLI를 호출하는 Adapter 한 종류
- JSON 기반 설정·상태와 Markdown 기반 계획·검토 보고
- 초기에는 별도 SDK나 데이터베이스 없이 시작

앞선 환경 확인에서는 Node.js v24.14.0과 Codex CLI 0.154.0이 확인되었다. CLI 도움말에서 JSON 이벤트, 결과 스키마, 세션 재개 기능을 확인했다. 이는 실제 하네스의 로그인·모델 실행·권한 통제·복원 검증이 완료됐다는 뜻은 아니다.

### 폴더와 Git 경계

- 이 계획 문서는 사용자 요청에 따라 Decision Desk의 `develop-plan`에 둔다.
- 하네스 코드는 Decision Desk 내부가 아닌 같은 상위 폴더의 `development-harness`에 분리하는 것을 제안한다.
- 현재 Git 저장소 루트는 `decision-desk`가 아니라 상위 `AI Development`다.
- 따라서 폴더 분리와 독립 Git 저장소 생성은 다르다. 저장소 초기화, 기존 Git 구조 변경, 원격 설정을 자동 수행하지 않는다.
- 최종 코드 위치와 저장소 관리 방식은 착수 시 확인하며, 현재 문서 작성으로 새 하네스 폴더를 만들지 않는다.

Decision Desk 최종 제품의 “설치 없이 오프라인 실행”과 개발용 하네스의 런타임·AI 연결 요구는 별개다. 하네스의 기술 선택으로 최종 제품의 실행 요구를 바꾸지 않는다.

## 12. 구현 순서 제안

1. 이 문서의 v0.1 범위, 승인 정책, 작업 경계를 확인한다.
2. 실제 AI 호출 없이 Profile·Work Item 검사, 단계 전환, 승인 대기·재개를 검증할 작은 Runner를 만든다.
3. Codex CLI Adapter를 연결하고 역할별 실행·결과 수신·권한 경계를 확인한다.
4. Reviewer·Tester 흐름, 검증 증거 수집, 제한된 수정 반복을 연결한다.
5. 비정상 종료, 재개, 코드 변경 후 승인 무효화와 필수 검증 실패를 시험한다.
6. Decision Desk용 Profile과 작은 별도 예제 Profile로 공통 Core의 재사용성을 확인한다.
7. 사용자에게 실행 결과와 미검증 사항을 제시하고 v0.1 완료 검토를 받는다.

이는 구현 순서의 기본안이며, 이 문서 작성만으로 구현이 시작되거나 추가 설치·외부 실행이 승인된 것으로 취급하지 않는다.
