# AI Development Harness — 축소 MVP 계획

- 작성일: 2026-09-14
- 문서 버전: 축소안 0.4
- 상태: 대화에서 정리한 축소 범위와 우선순위 제안
- 목적: 첫 버전의 지원 조건과 완료 기준을 좁혀 핵심 개발 흐름을 실제로 검증한다.
- 관련 문서: [기존 v0.6 계획](./archive/ai-development-harness-mvp-plan-v0.6.md)

이 문서는 기존 계획을 자동으로 대체하거나 구현 착수를 승인하는 문서가 아니다. 최신 대화의 축소 방향을 독립적으로 정리한 검토 자료다. 특히 기존 문서의 로컬 Git 자동화와 달리, 이 안에서는 모든 Git 쓰기를 사용자의 수동 작업으로 둔다.

## 1. 제품 목표

> 개발 환경이 준비된 프로젝트에서 사용자가 Phase 계획을 승인하면, 하네스가 구현·테스트·리뷰·제한된 수정을 진행하고 사용자가 확인할 결과물을 제공하는 로컬 CLI를 만든다.

첫 버전에서 증명할 핵심은 하나다. 기획을 읽고 승인된 Phase를 실행한 뒤, 검증 근거와 결과물을 전달하고 중단 후에도 필요한 단계부터 이어갈 수 있어야 한다.

범용 환경 구축, 복잡한 예외 처리, 실행 비용 최적화는 핵심 흐름을 검증한 후에 확장한다.

개발 방식에는 단계적 dogfooding을 적용한다. 최소 실행 흐름을 별도 예제에서 확인한 뒤, 동작이 확인된 하네스로 하네스 자신의 작은 기능을 개발한다. 별도 제품 기능이나 자동 업데이트 시스템을 추가하지 않고 기존 Phase 실행 흐름을 실사용한다(10.1~10.4).

## 2. 지원 범위와 시작 조건

### 2.1 지원 대상

- 신규 프로젝트: 기본 코드와 테스트 환경이 준비된 템플릿에서 시작한다.
- 기존 프로젝트: 실행 방법과 검증 명령이 준비되어 있고 기본 검사가 통과하는 코드에서 시작한다.
- 기존 기능 변경도 Phase 계획으로 처리한다. 작은 변경은 Task가 적은 작은 Phase로 표현할 수 있다.
- 한 프로젝트에서 Task를 순차 실행한다. 첫 버전의 검증 대상 기술 구성은 한 종류로 한정한다.

### 2.2 사용자가 준비할 것

| 준비물 | 내용 |
|---|---|
| 프로젝트 폴더 | 신규 템플릿 또는 기존 코드 |
| Markdown 기획문서 | 개발·변경할 기능과 제약조건 |
| 개발 환경 | 필요한 런타임과 패키지 설치 |
| 검증 명령 | 실제 실행 가능한 단위·통합 테스트 명령 |
| AI 실행 환경 | 사용할 실행 도구와 인증 |

새 프로젝트에 사용할 템플릿은 사용자가 준비할 수 있다. 하네스가 제공하는 템플릿 패키지는 P1 추가 후보이며 P0 실행의 필수 기능은 아니다.

### 2.3 시작할 수 없는 경우

- 필수 도구나 검증 명령이 없으면 준비할 내용을 안내하고 중단한다.
- 기본 검사 실패는 결과와 원인을 보고한다. 기존 실패를 자동 허용하거나 성공으로 바꾸지 않는다.
- 도구 미설치, 실행 권한 문제, 기획 모순은 코드 수정 재시도로 해결하지 않는다.
- 검증 명령이 실제 테스트를 실행했는지 확인한다. 테스트가 발견되지 않은 상태를 제품 검증 통과로 취급하지 않는다.
- 기획상 구현을 막는 결정이 빠졌으면 필요한 질문을 한다. 별도 기획 검토 기능을 사용하지 않아도 적용한다.

Git 저장소와 커밋은 필수 조건이 아니다. 사용자의 미커밋 변경은 시작 기준선에 포함해 보존하며, 무조건 commit이나 stash를 요구하지 않는다.

## 3. 사용자 흐름

```text
프로젝트 등록·실행 범위 확인·기본 검사
→ 기획문서와 관련 코드 확인
→ 전체 Phase 계획 + 현재 Phase 상세 계획
→ 사용자 계획 승인
→ Task 순차 구현·테스트·리뷰·수정
→ Phase 통합 검증
→ 결과 보고서 생성
→ 사용자 UI 확인·인수 또는 수정 요청
→ 다음 Phase 상세화·승인
```

전체 Phase의 목표와 순서를 먼저 정하고, 현재 Phase만 실행 가능한 Task로 상세화한다. 처음에는 전체 계획과 첫 Phase 상세 계획을 함께 제시할 수 있다. 승인받은 내용이 그대로라면 반복 승인받지 않는다.

## 4. 우선순위

P0는 첫 버전의 필수 범위다. P1은 핵심 흐름을 완성한 뒤 첫 출시 포함 여부를 판단할 후보이며, 자동으로 필수 범위가 되지 않는다. P2는 첫 버전에서 구현하지 않는다.

| 우선순위 | 항목 | 구현 범위 |
|---|---|---|
| P0 | CLI 초기화·기본 검사 | 경로·문서·명령·실행 환경 확인, 시작 기준선 기록 |
| P0 | 계획 생성 | 전체 Phase와 현재 Phase Task·완료 기준 작성 |
| P0 | 요구사항 대응표 | 요구사항을 Phase, 현재 Task, 재사용 또는 제외 사유에 연결 |
| P0 | 관련 코드 조사·요약 | 해당 Phase에 필요한 구조·규칙·재사용 근거를 계획에 기록 |
| P0 | 승인 | 전체 계획·Phase 계획·결과 인수, 중요한 범위·위험 변경 확인 |
| P0 | 단일 실행 흐름 | Developer → Validation Runner → Reviewer, 필요 시 수정·재검증 |
| P0 | 상태·재개 | SQLite 기록, 실행 소유권, 단계별 재개, 불일치 시 중단 |
| P0 | 실행 비용·리뷰 효과 기록 | 역할별 AI 호출 수, 단계별 실행 시간, 별도 승인 대기 시간, 리뷰 지적과 처리 결과 |
| P0 | 결과 보고·수정 요청 | 짧은 보고서, 재사용 항목의 검증 결과, 같은 범위 재작업 또는 계획 변경 |
| P0 | 단계적 dogfooding | 별도 예제로 최소 흐름 확인 후 하네스 기능 한 건을 자체 실행으로 개발·검증·인수. 실행 버전과 수정 대상 분리 |
| P1 | 선택적 기획 검토 | 중요한 누락·모순·질문을 짧게 출력. 자동 수정·점수화·이력 시스템 제외 |
| P1 | 기본 템플릿 한 개 | 선정한 기술 구성의 최소 코드·테스트 환경. 선택기·범용 자동 설치 제외 |
| P2 | 자동 준비·예외 관리 | 부트스트랩 자동화, 기존 실패 허용, 자동 신규·기존 판별 |
| P2 | 고급 계획·실행 | 커버리지 분석 엔진, 컨텍스트 자동 갱신, Workflow 자동 분류 |
| P2 | 고급 수정·복구 | Phase 없는 자연어 요청, 부분 무효화 최적화, 자동 충돌 복구 |
| P2 | 지원 확대 | 다중 AI 도구, 여러 기술 구성, 병렬 Task, 웹 대시보드 |

기획 검토를 P1로 두어도 개발을 막는 불확실성 확인은 P0에 포함한다. 요구사항 대응표는 자동 완전성 판정기가 아니며, 사용자가 계획 누락을 확인할 수 있는 자료다.

## 5. 계획 산출물

### 5.1 전체·현재 Phase 계획

전체 계획에는 Phase 목표·순서·종료 조건을 적는다. 현재 Phase의 Task에는 작업 범위, 완료 기준, 선행 작업, 관련 코드·요구사항, 검증 방법과 위험 요소를 적는다.

### 5.2 간단한 요구사항 대응표

| 요구사항 | 처리 계획 | 근거·확인 방법 |
|---|---|---|
| 파일 업로드 | P1에서 구현 | 업로드 단위·통합 테스트 |
| 결과 저장 | P2에서 구현 | P2 상세화 시 검증 방법 구체화 |
| 기존 로그인 | 재사용 | 관련 코드 위치와 기존 인증 테스트 확인 |
| 일괄 처리 | 이번 범위 제외 | 제외 이유를 계획 승인 자료에 기재 |

나중 Phase를 아직 상세화하지 않았다는 이유로 모든 요구사항을 현재 Task에 연결하지 않는다. 재사용은 코드의 존재뿐 아니라 현재 요구사항 충족 여부를 확인한다. 조사되지 않은 항목은 확인 필요로 표시한다.

재사용은 계획 시점의 판단이며 완료 근거가 아니다. 재사용 항목에도 관련 Phase와 확인할 요구사항·검증 방법을 연결하고, 해당 Phase 인수 시 9장의 보고서에 실제 결과를 포함한다. 구현 Task를 만들지 않은 항목도 이 확인에서 빠뜨리지 않는다.

### 5.3 관련 코드 요약

Planner는 해당 Phase에 필요한 코드와 기존 지침을 읽고 다음을 계획에 짧게 기록한다.

- 관련 파일과 주요 진입점.
- 재사용할 기능과 수정할 영역.
- 따라야 할 구조·테스트·오류 처리 규칙과 근거 파일.
- 명시된 규칙과 코드에서 추정한 패턴의 구분.

별도의 `codebase-context.md` 갱신 시스템은 만들지 않는다. Developer·Reviewer는 요약과 함께 실제 관련 코드를 확인한다.

## 6. 구현·검증·수정

Fast·Standard·Strict를 나누지 않고 단일 순차 Workflow로 시작한다.

**Reviewer를 P0에 유지하는 이유:** Developer가 구현과 테스트를 함께 작성하므로, 요구사항을 잘못 이해한 코드와 그 코드에 맞춘 테스트가 함께 만들어질 수 있다. 테스트 통과만으로 요구사항 충족을 판단하지 않고, Reviewer가 별도 세션에서 승인된 요구사항·실제 코드·테스트를 대조해 누락과 잘못된 해석을 확인한다. 역할 분리 자체가 정확성을 보장하지는 않으므로 실제 실행 결과와 사용자 인수도 유지한다.

첫 MVP에서는 작은 Task에도 Reviewer를 적용한다. 이후 검토 생략 여부는 인상이나 호출 수만으로 결정하지 않고, 8장의 실행 기록과 실제 수정으로 이어진 지적을 바탕으로 검토한다.

```text
Task 승인 범위·선행 조건 확인
→ Developer 구현·필요한 테스트 작성
→ Validation Runner가 등록된 검사 실행
→ 통과 후 Reviewer가 요구사항·코드·테스트 검토
→ 필수 수정이 있으면 Developer 수정
→ 변경된 코드에서 필요한 검사·리뷰 다시 수행
→ Task 기술적 완료 기록
```

- 자동 검증은 단위·통합 테스트를 중심으로 한다. 준비된 프로젝트의 타입 검사·린트·빌드는 필요한 경우 함께 실행한다.
- 브라우저 UI 테스트는 사용자가 수행한다.
- 실패·미실행·중단된 필수 검사를 성공으로 처리하지 않는다.
- 검증·리뷰 결과를 실제 코드 내용과 승인된 계획 버전에 연결한다.
- Task 완료 후에도 Phase 인수 전에는 현재 최종 코드에서 Phase 통합 검증을 수행한다.
- 자동 수정 한도는 설정 가능하게 하며 초기 기본값 2회를 제안한다. 승인 대기는 횟수에 포함하지 않는다.
- 한도 초과 시 원인·시도 내역·남은 결과를 보고하고 중단한다.

첫 버전에는 검사 결과 재사용을 위한 정교한 영향 분석을 넣지 않는다. 재구현은 필요한 부분만 하고, 관련 Phase 검사는 보수적으로 다시 실행한다.

## 7. 승인·수정 요청·권한

### 7.1 사용자 판단 지점

- 전체 계획과 현재 Phase의 개발 범위·완료 기준 승인.
- 주요 설계·범위 변경 및 새로운 위험 동작 확인.
- Phase 결과 확인과 인수.
- 반복 실패나 환경 문제 발생 시 진행 방향 결정.

무응답은 승인 대기다. 사용자가 확인한 계획·산출물 버전에 승인을 연결하며, 실질적으로 달라진 대상에 이전 승인을 적용하지 않는다.

### 7.2 결과 수정 요청은 두 경로

| 상황 | 처리 |
|---|---|
| 승인된 요구사항대로 동작하지 않음 | 같은 Phase에서 수정·리뷰·재검증 |
| 원하는 기능이나 범위를 변경함 | 계획 수정·승인 후 구현 |

피드백 원문과 처리 결과를 기록한다. 상세 반려 유형 자동 분류, Task별 승인 승계 최적화는 제외한다. 구현 누락을 무조건 새로운 요구사항으로 취급하지 않는다.

### 7.3 실행 권한과 Git

- 승인된 범위의 일반 파일 수정과 확인된 검증 명령은 자동 진행한다.
- 지원하는 실행 도구에서 실제로 통제할 수 있는 동작만 자동화한다.
- 설치·외부 전송 등 사전 통제를 지원하지 않는 위험 작업은 실행 전에 차단하고 사용자 수동 처리로 넘긴다.
- 작업 에이전트가 승인·검증 정책이나 승인 기록을 변경해 권한을 얻을 수 없어야 한다.
- Git 초기화·Branch 생성 및 전환·staging·commit·push·PR·merge·배포는 수행하지 않는다. 사용자 수동 작업이다.

첫 실제 Adapter 연결 시 권한 경계를 확인한다. 이를 확인하지 못한 작업을 승인 문구나 AI의 자기 보고만으로 자동화하지 않는다.

## 8. 상태 저장과 중단·재개

실행 상태·승인·검사 근거는 SQLite에 저장한다. 프로젝트 폴더에는 설정·계획·보고서를 두고, 실행 DB와 로그는 OneDrive 밖의 로컬 저장소에 둔다.

필수 기록은 프로젝트·Run·Phase·Task 식별자, 계획·코드 버전, 현재 단계, 승인 대상과 결과, 명령별 검사 결과, 리뷰 결과, 수정 횟수, 시작 기준선과 중단 사유다.

- 코드 버전은 Git 커밋 없이 파일 내용으로 식별한다. 로그·캐시·보고서 등 생성물의 제외 범위를 정한다.
- 같은 프로젝트의 실행 소유권은 한 실행만 획득하도록 한다. 상태 조회 후 동시에 두 실행이 시작되지 않아야 한다.
- 정상 중단 후에는 기록된 단계에서 재개한다.
- 끝나지 않은 검사 결과를 성공으로 추정하지 않는다. 잔여 실행 프로세스를 확인한 뒤 필요한 검사를 다시 실행한다.
- 코드 작성 중 종료됐다면 부분 결과를 먼저 확인하고 이어서 작업한다.
- 기록과 실제 파일이 예상과 다르면 차이를 보여주고 중단한다. 자동 병합·되돌리기는 하지 않는다.
- 사용자의 기존 변경을 보존한다. 실행 중 사용자가 같은 파일을 수정한 경우도 확인 없이 덮어쓰지 않는다.
- 사용자 수동 Git 작업이 코드·계획·실행 입력을 바꾸지 않았다면 Git 메타데이터 변화만으로 재개를 차단하지 않는다.

전체 자동 복구와 장치 간 상태 이전은 지원하지 않는다. 단계별 재개를 위한 기록·동시 실행 방지·파일 보존을 우선한다.

### 8.1 실행 비용과 리뷰 효과의 최소 기록

별도 대시보드나 비용 정산 엔진을 만들지 않고, 기존 실행·검토 기록에 다음 정보를 남겨 Phase별로 집계한다.

| 기록 | 집계 기준 |
|---|---|
| 역할별 AI 호출 수 | Planner·Developer·Reviewer의 실제 호출 시도를 기록한다. 최초 구현·수정·재검토·실패 후 재호출을 구분하며, 재개 시 이전 기록을 중복 집계하지 않는다 |
| 단계별 실행 시간 | 각 AI 호출과 검증 명령의 시작·종료, 성공·실패·중단 여부를 기록한다. 종료가 확인되지 않은 구간은 정확한 소요 시간으로 추정하지 않는다 |
| 사용자 승인 대기 시간 | 실행 시간과 별도로 기록한다. 하네스가 꺼져 있던 중단 시간도 실행 시간에 합산하지 않는다 |
| 리뷰 지적과 처리 결과 | 지적 식별자·중요도·내용과 수정 확인·오탐·보류 등 처리 결과 및 근거를 연결한다. 재검토에서 같은 지적을 반복해도 새 문제로 중복 집계하지 않는다 |

- AI가 제안한 지적 수와 실제 수정이 확인된 지적 수를 구분한다. 수정했다는 Developer의 자기 보고만으로 해결 처리하지 않고 후속 검토·검증 근거를 연결한다.
- 보류한 지적 중 필수 완료 조건에 해당하는 문제는 완료를 막는다. 보류 분류가 검증 예외를 자동 허용하지 않는다.
- Phase에 직접 속하지 않는 전체 계획 호출은 프로젝트 계획 기록으로 따로 표시해 여러 Phase에 중복 합산하지 않는다.
- 기본 측정 대상은 호출 수와 소요 시간이다. 제공되지 않은 토큰 수나 금액을 추정하지 않으며 별도 과금 API 연동은 추가하지 않는다.
- 작은 변경과 일반 기능 개발을 구분해 기록을 해석한다. 작업 범위가 다른 Phase의 총시간만 비교해 Workflow 효율을 단정하지 않는다.

## 9. Phase 결과 보고서와 완료

보고서는 1~2페이지 내외의 본문을 목표로 하며, 상세 로그는 별도 기록으로 연결한다.

| 항목 | 내용 |
|---|---|
| 개발 결과 | 구현한 기능, 산출물 위치, 실행 방법 |
| 검증 결과 | 실제 실행한 단위·통합 테스트와 결과, 재사용 항목별 확인 방법·근거·결과, 미검증 항목 |
| 주요 문제 | 의미 있는 오류·처리 결과·남은 문제 |
| 계획 변경 | 승인받아 변경한 내용과 이유 |
| 사용자 확인 | UI 확인 순서와 기대 결과 |
| 실행 요약 | 역할별 AI 호출 수, 단계별 실행 시간, 별도 승인 대기 시간, 리뷰 지적 수와 처리 결과 |

실행 요약은 SQLite의 실행·리뷰 기록에서 집계한다. 중요한 지적의 내용과 해결 여부를 짧게 보여주고, 세부 기록은 링크로 연결해 본문 분량을 유지한다.

### 9.1 재사용 항목의 인수 시점 확인

현재 Phase가 의존하거나 충족해야 하는 요구사항에 해당하는 재사용 기능을 최종 산출물에서 확인한다. 관련 없는 기존 기능 전체를 다시 조사하는 기능은 추가하지 않는다.

| 재사용 항목 | 확인할 요구사항 | 확인 방법·근거 | 결과 |
|---|---|---|---|
| 기존 로그인 | 비밀번호 로그인 | 실제 실행한 인증 테스트 기록 | 통과 |
| 기존 로그인 | 새 요구사항의 2단계 인증 | 관련 코드·테스트 확인 결과 지원 없음 | 미충족 — 보완 작업 필요 |
| 기존 파일 저장 | 저장 후 다시 읽기 | 실제 실행한 저장·조회 통합 테스트 기록 | 통과 |

위 표는 형식 예시이며 실제 테스트 결과가 아니다. 코드나 타입이 존재한다는 사실만으로 자동 검증 통과를 표시하지 않는다. 자동 검사와 사용자 수동 확인을 구분하고, 확인하지 못한 항목은 미검증으로 표시한다.

- 재사용 기능이 승인된 요구사항을 충족하지 못하면 기존 요구사항의 구현 누락으로 보고 보완한다. 이미 계획에 있던 요구사항을 새 요청으로 바꾸지 않는다.
- 확인 과정에서 사용자가 새로운 요구사항을 추가하면 계획 변경·승인 경로를 적용한다.
- 필수 인수 조건인 재사용 항목이 미충족·미검증 상태이면 Phase를 완료 처리하지 않는다. 사용자 수동 확인 항목은 확인 결과를 기록한 뒤 인수한다.

### 9.2 Phase 완료 판정

실패 상태에서도 결과 보고서는 생성한다. 다만 필수 조건 미충족을 결과 승인만으로 완료로 바꾸지 않는다. 일부 범위를 제외하려면 계획과 완료 기준을 변경해 승인받은 후 해당 범위를 검증한다.

Task의 기술적 완료와 Phase의 사용자 인수를 구분한다. 최종 산출물을 검증하고 사용자가 인수하면 Phase가 완료된다. Git 반영은 완료 조건에 포함하지 않는다.

## 10. 구현 순서 제안

| 순서 | 목표 | 확인할 결과 |
|---|---|---|
| 1 | Runner 기반 | 가짜 Adapter로 상태·승인 대기·실패·중단·재개·동시 실행 방지 검증 |
| 2 | 실제 연결과 계획 | 실제 AI Adapter의 최소 호출·실행 권한 경계 확인, 초기화·계획·대응표·코드 요약 생성 |
| 3 | Phase 실행·dogfooding 진입 | 구현·테스트·리뷰·제한된 수정·실행 기록·최소 결과 안내 연결. 별도 예제 Task 한 건의 승인부터 결과 확인·중단 후 재개까지 검증하고 실행용 버전을 고정 |
| 4 | 전달과 실사용 | 고정한 하네스로 보고서·상태 출력 등 작은 자체 기능 한 건을 개발·검증·인수. 별도로 신규 및 기존 예제에서 각 한 Phase 실행. UI·재사용 항목 확인과 호출 수·시간·리뷰 효과 점검 |

P1 기능은 P0의 전체 흐름이 동작한 뒤 비용과 실제 사용 필요성을 보고 선택한다. 코드 조사와 대응표를 별도의 분석 제품으로 확대하지 않는다.

### 10.1 Dogfooding 적용 단계

| 단계 | 개발 방법 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| A. 최소 기반 구축 | 기존 AI 코딩 도구로 Runner·승인·구현·검증·리뷰·기록·재개를 개발 | 기본 상태·권한·파일 보존 규칙이 검사됨. 아직 자체 개발 실적으로 계산하지 않음 |
| B. 별도 예제 확인 | 준비된 작은 예제에서 실제 하네스로 Task 하나 실행 | 계획 승인 → 구현 → 테스트 → 리뷰 → 최소 결과 안내 → 사용자 확인이 연결되고 중단·재개가 확인됨 |
| C. 작은 자체 기능 개발 | 확인된 실행용 하네스로 개발 저장소의 작은 Phase 실행 | 해당 기능의 코드·테스트·리뷰·결과 확인이 실제 하네스 흐름으로 완료됨 |
| D. 다음 버전 사용 | 수정 버전을 별도 실행으로 검증하고 사용자 결과 확인 후 다음 Run부터 사용 | 핵심 회귀 검사가 통과하고 새 버전이 기존 기록을 잘못 읽거나 변경하지 않음 |

첫 dogfooding 대상은 아직 남아 있는 P0 작업 중 보고서 항목, `status` 표시, 오류 안내처럼 범위가 좁은 기능으로 고른다. 이를 위한 새 기능을 일부러 추가하지 않는다. Phase 없는 요청 기능은 MVP2이므로 첫 MVP에서는 Task가 적은 작은 Phase로 실행한다.

### 10.2 실행 버전과 개발 버전 분리

- **실행용 A:** 동작이 확인된 고정 설치본 또는 복사본. 이번 Run을 제어한다.
- **개발용 B:** A가 수정할 하네스 개발 저장소. 코드와 테스트의 변경 대상이다.
- A의 실행 파일·의존성·역할 지침·현재 승인 정책은 B의 수정 경로와 분리한다. 개발 저장소를 실시간으로 참조하는 실행 방식으로 A를 구동하지 않는다.
- A가 사용하는 Run DB·승인 기록은 B와 테스트 프로세스가 변경할 수 없도록 실행 권한을 제한한다. B의 테스트는 별도의 임시 DB·작업 폴더를 사용한다.
- Run 도중 A를 수정하거나 B로 교체하지 않는다. B를 검증한 뒤 사용자가 결과를 확인하면 다음 Run부터 사용할 버전을 선택한다.
- 버전 교체는 수동으로 수행하고 이전 실행본을 보존한다. 자동 업데이트·버전 배포 기능을 만들지 않는다. Git 작업도 사용자 수동 원칙을 유지한다.
- 상태 형식이 바뀌면 기존 DB를 새 버전으로 바로 열지 않는다. 호환성을 확인하고, MVP에서는 새 시험 Run으로 검증할 수 있다. 진행 중인 Run을 다른 버전으로 자동 이전하지 않는다.

### 10.3 자기 검증의 한계와 보호 기준

dogfooding은 하네스의 사용성을 확인하는 방법이며, 하네스 자신의 완료 선언만으로 정확성을 보장하지 않는다. 첫 단계에서 다음 핵심 회귀 검사를 준비하고 수정 버전에도 적용한다.

- 계획 승인 전 제품 코드 구현이 시작되지 않는다.
- 실패·미실행·중단된 필수 검사가 통과로 기록되지 않는다.
- 같은 프로젝트의 동시 수정과 사용자 변경 훼손을 막는다.
- 재개 시 승인·계획·실제 파일 상태를 확인한다.
- 작업 에이전트가 실행용 하네스의 정책이나 승인 기록을 바꿔 통과하지 못한다.

Developer가 수정 버전의 코드와 테스트를 함께 바꿀 수 있으므로, 기존 핵심 검사를 기준으로 보존해 변경 내용을 대조한다. 기준·검증 정책을 완화하는 변경은 기존 7장의 승인 경로로 처리하고, Reviewer가 요구사항·코드·테스트 변경을 함께 검토한다. 새 버전은 별도 실행으로 실제 CLI 동작까지 확인한다.

자체 개발 중 실행용 하네스의 결함이 진행을 막으면 파일과 실패 기록을 보존하고 중단한다. 기존 AI 코딩 도구로 기반을 수정한 뒤 검증·재개하며, 이 수동 개입은 dogfooding 결과에 표시한다. 하네스가 아직 처리하지 못하는 작업을 억지로 자기 자신에게 맡기지 않는다.

### 10.4 Dogfooding 기록과 외부 예제 검증

별도 관리 시스템을 만들지 않고 기존 8.1 실행 기록과 9장 보고서를 활용한다. 자체 개발 Run에는 실행용 버전과 수정 대상 버전을 구분해 남기고 다음 경험을 짧게 기록한다.

- 계획과 결과 자료만으로 사용자가 승인·인수할 수 있었는가.
- 불필요한 대기·반복 질문·수동 개입이 어디에서 발생했는가.
- 실패 원인과 재개 방법을 알 수 있었는가.
- AI 호출 수·소요 시간과 Reviewer가 발견한 문제는 어떠했는가.

발견 사항은 현재 P0의 결함, 필요한 구현 조정, 이후 기능 후보로 나눠 다룬다. 사용 중 불편이 발견됐다는 이유만으로 MVP 범위를 자동으로 확대하지 않는다.

하네스 저장소에서의 성공은 별도 프로젝트 재사용성의 증거를 대체하지 않는다. 첫 MVP 완료 전에는 선정한 기술 구성의 신규 및 기존 예제에서 각각 한 Phase를 확인한다. 개발 검증용 예제는 P1의 사용자 배포용 템플릿 기능과 구분한다.

## 11. MVP 완료 기준

- [ ] 준비된 프로젝트에서 초기화와 기본 검사를 수행한다.
- [ ] 전체 Phase와 현재 Phase 상세 계획, 요구사항 대응표를 제시한다.
- [ ] 기존 프로젝트에서는 관련 코드·규칙·재사용 근거를 계획에 남긴다.
- [ ] 사용자 계획 승인 전에 제품 코드를 구현하지 않는다.
- [ ] 승인된 범위에서 구현·검증·리뷰·제한된 수정을 순차 수행한다.
- [ ] 필수 검사 실패·미실행·테스트 미발견을 통과로 표시하지 않는다.
- [ ] 검증한 코드·계획과 결과 승인 대상을 연결한다.
- [ ] Reviewer가 별도 세션에서 요구사항·실제 구현·테스트를 대조하고 필수 지적의 처리 근거를 남긴다.
- [ ] 역할별 실제 AI 호출 수와 단계별 실행 시간을 기록하며 승인 대기·중단 시간을 구분한다.
- [ ] 재개·재검토 시 호출과 같은 지적을 중복 집계하지 않고, 지적 수와 수정이 확인된 지적 수를 구분한다.
- [ ] 현재 Phase의 재사용 항목도 최종 산출물에서 확인 방법·근거·결과를 제시한다. 필수 항목이 미충족·미검증이면 인수를 막는다.
- [ ] 반복 실패 시 중단하고 시도 내역을 보고한다.
- [ ] 같은 프로젝트의 동시 수정과 사용자 변경 훼손을 막는다.
- [ ] 중단 후 필요한 단계부터 재개하며 불일치 상태는 자동으로 덮어쓰지 않는다.
- [ ] 지원하지 않는 위험 동작은 실행 전에 차단한다.
- [ ] 짧은 Phase 결과 자료를 제시하고 사용자 인수·수정 요청을 처리한다.
- [ ] Git 쓰기와 배포를 수행하지 않는다.
- [ ] 선정한 기술 구성의 신규 템플릿과 기존 프로젝트에서 각각 한 Phase를 끝까지 수행한다.
- [ ] 별도 예제에서 최소 실행 흐름·중단·재개를 확인한 후 자체 개발을 시작한다.
- [ ] 고정한 실행용 하네스와 수정 대상 코드·테스트 환경을 분리하고, 실행 중인 정책·승인 DB를 개발 대상이 변경하지 못한다.
- [ ] 기존 P0의 작은 하네스 기능 한 건을 하네스 자체의 계획·승인·구현·검증·리뷰·사용자 인수 흐름으로 완료한다.
- [ ] 수정 버전은 핵심 회귀 검사와 별도 실행으로 확인하며, 사용자 결과 확인 후 다음 Run부터 사용한다.
- [ ] dogfooding에서 사용한 버전·수동 개입·실행 비용·발견 문제를 기존 기록과 보고서에 남긴다.

## 12. 사용자가 다음에 할 일

우선순위 표를 새로 작성할 필요는 없다. 이 문서의 P0·P1·P2 분류를 기준으로 다음만 판단하면 된다.

1. **필수 범위 확인:** P0만으로도 본인이 실제로 사용할 수 있는지, 빠진 핵심 기능이 있는지 확인한다.
2. **추가 후보 선택:** 선택적 기획 검토와 기본 템플릿 제공을 첫 버전에 포함할지 판단한다. 별도 선택 전에는 P0만 구현 범위로 본다.
3. **첫 실사용 대상 지정:** 환경이 준비된 프로젝트와 시험할 Phase 하나를 고른다. 기존에 제안된 Decision Desk는 후보이며 실행 환경 준비 여부를 먼저 확인한다.

세부 개발 Task 분해와 검증 기준 작성은 이 범위를 바탕으로 하네스 개발 계획에서 수행한다. 정확한 일정은 기술 구성과 실제 Adapter 권한 검증 후 산정한다.

## 14. MVP2 확장 계획

### 14.1 목표와 첫 MVP와의 관계

> 첫 MVP의 Phase 실행 흐름을 유지하면서 프로젝트를 시작하는 수고와 작은 수정의 계획 부담을 줄인다.

이 절은 첫 MVP 이후의 확장 기본안이다. 첫 MVP의 필수 범위를 늘리지 않으며, 4장의 P2 항목 전체를 MVP2에서 구현한다는 뜻도 아니다. P0·P1·P2는 우선순위이고, MVP2는 두 번째 제품 개발 범위다.

MVP2의 기본 범위는 **선택한 템플릿으로 시작하기**와 **Phase 없는 작은 수정 요청** 두 가지로 제한한다. 기획 검토·검증 최적화 등은 실사용에서 필요성이 확인될 때 추가 범위를 검토한다.

### 14.2 착수 조건

- 첫 MVP에서 준비된 신규·기존 프로젝트의 Phase를 각각 인수까지 실행한다.
- 승인 전 구현, 잘못된 검증 통과, 사용자 변경 훼손, 중복 실행 등 핵심 흐름의 결함을 먼저 해결한다.
- 실사용 기록에서 수동 환경 준비, 작은 수정의 계획 부담, 테스트·리뷰 대기 중 무엇이 반복되는지 확인한다.
- 실제로 해결할 문제가 있는 확장부터 선택한다. 아래 순서는 기본안이며, 근거와 함께 변경할 수 있다.
- 일정은 첫 MVP의 실행 기록과 선택한 확장 범위를 바탕으로 산정한다. 필요성이 확인되지 않은 기능을 채우기 위해 MVP2를 늘리지 않는다.

### 14.3 기본 확장 A — 프로젝트 시작 지원

**해결할 문제:** 신규 프로젝트를 시작할 때마다 사용자가 같은 기본 코드와 테스트 설정을 준비해야 한다.

**지원 범위**

- 첫 MVP에서 검증한 기술 구성 한 종류와 기본 템플릿 한 개만 지원한다.
- `init`에서 신규 템플릿 사용 또는 기존 프로젝트 연결을 선택하게 한다. 자동 판별은 보조 안내로만 사용하며 사용자 선택을 바꾸지 않는다.
- 신규 템플릿 사용 시 생성할 위치·파일·검증 명령을 제시한다. 기존 파일을 자동으로 덮어쓰지 않는다.
- 기존 프로젝트에서는 알려진 매니페스트와 설정을 바탕으로 검증 명령 후보를 제안하고 확인받는다. 알아내지 못하면 기존처럼 사용자가 입력한다.
- 패키지 설치는 실행 전에 해당 권한을 확인한다. 지원하는 실행 환경에서 사전 통제가 되지 않으면 사용자가 설치한 뒤 재개한다.
- 기본 템플릿에 포함된 실제 샘플 테스트를 실행해 준비 상태를 확인한다. 명령이 존재하거나 테스트 0개로 성공했다는 이유만으로 준비 완료 처리하지 않는다.
- 기존 프로젝트의 baseline 실패 허용은 추가하지 않는다. 기본 검사가 통과해야 일반 개발을 시작한다.

**구현 방식:** 기존 Project Loader·Validation Runner·승인 기록을 확장한다. 임의 스택을 설계하고 구성하는 범용 부트스트랩 엔진은 만들지 않는다. 첫 MVP에서 템플릿을 이미 제공했다면 중복 제작하지 않고 초기화 연결만 추가한다.

**완료 기준:** 지원 템플릿으로 만든 프로젝트가 실제 기본 검사를 통과하고 첫 Phase 계획으로 진입한다. 기존 파일이 있는 폴더와 명령 자동 감지가 실패한 프로젝트에서는 보존·수동 입력 경로가 동작한다.

### 14.4 기본 확장 B — Phase 없는 작은 수정 요청

**해결할 문제:** 문구·스타일·작은 버그 수정마다 형식적인 Phase를 만들고 전체 계획을 확인해야 한다.

```text
사용자의 명시적인 수정 요청
→ 관련 코드·요청 범위 확인
→ 작은 독립 Task 작성
→ 범위와 실행 권한 확인
→ 기존 구현·검증·리뷰 흐름 실행
→ 짧은 결과 안내·필요한 사용자 확인
```

- CLI의 명시적인 요청 진입점으로만 받는다. 일반 채팅을 자동 수집하지 않는다.
- 요청 원문, 해석한 범위, 완료 기준을 저장한다. 명확한 요청은 해당 범위의 승인 근거로 사용할 수 있으며, 모호하거나 중요한 범위 변경은 실행 전에 확인한다.
- 큰 기능 개발이나 영향이 불명확한 요청은 기존 Phase 계획 흐름으로 연결한다.
- 별도 실행 엔진을 만들지 않는다. 기존 Task 실행·수정 한도·검증·결과 기록을 재사용한다.
- Phase 없는 Task를 지원하도록 Run과 승인 대상의 연결을 확장하고, 기존 Phase Run의 재개가 유지되는지 확인한다.
- 진행 중인 작업이 있으면 순차 처리한다. 같은 프로젝트를 동시에 수정하지 않는다.
- 처음에는 첫 MVP의 단일 Workflow를 유지한다. 작은 요청 지원과 Fast 도입을 한꺼번에 구현하지 않는다.
- UI 변경은 자동 검사 결과와 사용자 화면 확인 필요를 구분한다. Git 작업은 수행하지 않는다.

**완료 기준:** 작은 요청을 Phase 생성 없이 실행·검증·보고할 수 있고, 중단 후 재개와 수정 요청이 동작한다. 큰 요청·모호한 요청·위험 동작은 적절한 계획 또는 승인 경로로 연결된다.

### 14.5 실사용 근거가 있을 때 추가할 후보

아래 항목은 MVP2 기본 완료 기준에 포함하지 않는다. 추가 채택 시 해결할 문제, 범위, 검증 기준을 먼저 정하고 필요하면 다음 버전으로 넘긴다.

| 후보 | 추가할 근거 | 처음 구현할 범위 |
|---|---|---|
| 선택적 기획 검토 | 개발 후 기획 누락·모순 때문에 재작업이 반복됨 | 짧은 검토 출력 또는 리포트. 첫 MVP에 이미 있으면 결과 개선만 수행 |
| 요구사항 대응표 점검 | 요구사항이 계획에서 반복적으로 빠짐 | 연결되지 않은 요구사항·확인 필요 항목 표시. 재사용도 근거와 검증 방법 유지 |
| Fast 경로 | 작은 변경에서도 테스트·리뷰 대기가 반복적으로 과도함 | 문서·한정된 스타일부터 적용. 동작 변경은 관련 테스트를 유지하고 애매하면 기본 Workflow 적용 |
| 기존 코드 요약 재사용 | 같은 구조 조사에 반복 비용이 크거나 규칙 누락이 발생함 | 근거 파일·기준 버전에 연결된 짧은 요약. 변경 시 다시 확인 |

Fast 채택 시 첫 MVP의 8.1 기록을 사용해 역할별 호출 수·검사 및 리뷰 시간·중요한 지적과 실제 처리 결과를 확인한다. 사용자 인수나 후속 사용에서 발견된 누락도 함께 검토한다. 빠르다는 이유로 필수 검증을 생략하거나 미검증 UI를 통과 처리하지 않는다. Standard·Strict까지 동시에 세분화할 필요는 없다.

### 14.6 MVP2 이후로 남길 항목

- 임의 기술 스택 선택과 범용 자동 환경 구축.
- 기존 실패를 허용하는 baseline 예외 관리와 테스트별 실패 비교.
- 정교한 부분 반려, 영향 분석과 승인·검사 결과 재사용 최적화.
- 사용자 변경의 자동 병합·충돌 복구, 장치 간 실행 상태 이전.
- 다중 AI 도구, 병렬 Task, 사용자 정의 Workflow, 웹 대시보드.

Git 쓰기와 배포 자동화, UI 자동 테스트는 향후 기본 확장 항목으로 넣지 않는다. 사용자가 제품 범위를 별도로 변경하지 않는 한 Git·배포와 UI 확인은 수동으로 유지한다.

### 14.7 구현 순서와 공통 완료 기준

| 순서 | 작업 | 확인할 결과 |
|---|---|---|
| 1 | 첫 MVP 실사용 기록 확인 | 실제 불편과 핵심 결함 구분, MVP2 범위 확정 |
| 2 | 프로젝트 시작 지원 | 템플릿·명령 안내에서 기본 검사와 Phase 계획까지 연결 |
| 3 | 작은 수정 요청 | Phase 없는 Task의 실행·승인·재개·결과 처리 |
| 4 | 기존 흐름 회귀 검증 | Phase 개발·사용자 인수·기존 Run 재개가 계속 동작 |
| 5 | 후보 평가 | 추가 후보의 필요성과 비용을 확인하고 채택 또는 연기 |

- [ ] 채택한 기본 확장의 완료 기준을 실제 프로젝트에서 확인한다.
- [ ] 첫 MVP의 승인·검증·사용자 변경 보존·동시 실행 방지 규칙을 유지한다.
- [ ] 첫 MVP에서 사용한 설정·상태의 호환성을 확인한다. 형식 변경이 필요하면 백업·이전·실패 시 중단 방식을 먼저 정한다.
- [ ] 신규 템플릿 시작과 작은 기존 코드 수정을 각각 실제로 수행하고 결과 확인까지 마친다.
- [ ] 추가된 자동화로 줄어든 수동 작업과 남은 제약을 기록한다. 실행 시간은 비슷한 작업·환경을 기준으로 비교한다.
- [ ] 위험 동작의 사전 승인, Git 수동 관리, 사용자 UI 확인 경계를 유지한다.
