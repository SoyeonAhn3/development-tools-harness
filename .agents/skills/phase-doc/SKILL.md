# Phase Doc Skill

각 Phase의 개발 계획과 실제 개발 내용(목적, 구현 상세, 설계 결정, 사용 예시)을 `Phase/` 디렉토리에 문서로 기록하고 갱신한다.

Verbatim의 `phase-doc` 구조를 기반으로 한다. 필요한 내용과 작업을 시작할 수 있을 정도의 디테일을 유지한다. 개발 중 발견한 변경은 Phase 문서에 반영하며, 일반적인 개발 진행을 이유로 이 스킬이나 템플릿을 수정하지 않는다.

## 이 프로젝트의 하네스 연결

이 스킬은 프로젝트에서 직접 문서를 작성할 때와 하네스의 계획 생성에서 함께 사용한다. 아래 두 실행 범위를 구분한다.

- **직접 문서 작성·갱신**: 아래 STEP 1–5와 표준 템플릿을 따른다.
- **하네스의 계획 생성**: 호스트가 이 파일과 `references/phase-template.md`를 읽어 해당 Run에 고정하고 Planner에 전달한다. Planner는 기획서에 근거한 구조화된 계획 JSON과 기술 구성(`technology.en`, `technology.ko`)을 작성한다. 전체 Phase의 목표·순서와 현재 Phase의 Task·완료 기준·검증 방법을 구분한다. 기술 선택이 미정이면 제안·미정으로 표시한다.
- 호스트는 템플릿의 `harness:overview:en/ko`, `harness:phase:en/ko` 블록으로 문서를 만든다. 문서 제목·배치·설명은 템플릿이 정하고, 필수 계획 데이터·인용·식별자 검사는 코드가 담당한다. 새 제목이나 설명을 바꿀 때 Python 문서 생성 코드를 수정할 필요가 없다.
- 새 산출물은 `Phase/Generated/<run-id>/vN/` 안에 저장한다. `PhaseN_EnglishName.md`는 영어 상단·구분선·한국어 하단의 통합 문서이며, `Plan.md`·`Plan_ko.md`는 전체 개요와 문서 링크다. 기존 Phase 문서는 덮어쓰지 않는다. 계획 초안 상태는 구현 완료·미시작 여부를 단정하지 않고, 구현·검증·사용자 인수 근거가 없음을 구분한다.
- 계획 생성 모드에서는 아래 README 갱신·dev-log·실제 개발 기록 갱신을 실행하지 않는다. 파일 접근·저장·승인은 호스트가 수행하며 스킬은 실행 권한을 부여하지 않는다. 대상 프로젝트에 있는 다른 스킬이나 전역 스킬을 자동 탐색하지 않는다.
- 사용한 두 파일의 원문·버전·해시를 보존한다. 스킬 변경은 새 Run부터 반영하며, 진행 중인 Run과 수정본은 등록 시 고정한 규칙을 사용한다. 기존 스킬 없는 Run은 종전 계획 형식을 유지한다.

이 프로젝트 사본은 전역 `phase-doc` 1.0에서 가져왔으며, 전역 사본과 자동 동기화하지 않는다.

## 사전 조건

- `Phase/` 디렉토리 존재 여부 확인 (없으면 생성)
- 대상 Phase 번호와 생성·업데이트 내용 파악
- 기존 Phase 문서가 있으면 Read 도구로 먼저 읽기

---

## STEP 1 — 현재 상태 파악

아래 파일들을 사용 가능한 파일 읽기·검색 도구로 확인한다:

```
Phase/PhaseN_*.md       — 기존 문서 확인 (파일명은 영어로 작성)
src/ 및 실제 소스 경로  — 구현된 모듈 확인
프로젝트의 스킬 경로    — 관련 스킬이 있을 때 확인
README.md, README_ko.md  — 프로젝트 상태와 전체 Phase 계획 확인
기획문서·프로젝트 지침  — 범위, 승인·완료 규칙, 기술 구성 확인
pyproject.toml 등 설정  — 결정된 언어·테스트 도구·실행 명령 확인
```

- 프로젝트에서 정한 언어·테스트 도구를 사용한다. 예를 들어 Python + pytest가 결정됐다면 그 선택을 Phase 문서에 기록한다. 특정 언어나 버전을 이 스킬의 필수 조건으로 두지 않는다.
- 계획 작성 시 전체 Phase의 목표·순서·선행 관계를 확인하고 현재 Phase만 실행 가능한 Task로 상세화한다. 전체 구성이 없고 구성을 요청받았다면 먼저 간단한 개요를 제안한다.
- 미결정 사항과 가정을 표시하고, 구현을 막는 기술 선택은 상세 실행 명령을 확정하기 전에 확인한다. 존재하지 않는 파일·명령은 예정으로 구분한다.

업데이트 유형을 아래 중 하나로 분류한다:

| 유형 | 해당 상황 |
|---|---|
| 신규 생성 | Phase 문서가 없음 |
| 완료 항목 추가 | 새 스킬/모듈 개발 완료 시 |
| 설계 변경 | 구현 방향이 바뀐 경우 |
| 상태 변경만 | 미시작 → 진행 중 → 완료 상태 전환 |
| 전체 갱신 | Phase 전체 재검토 |

## STEP 2 — 문서 작성 / 갱신

### 2-A. 신규 생성

```
references/phase-template.md 읽기
```
→ [표준 템플릿](references/phase-template.md)을 읽고 파일 쓰기 도구로 `Phase/PhaseN_[EnglishName].md` 생성

- 계획에는 Task별 작업 내용·완료 기준·검증 방법을 간결하게 적는다. 완료 기준은 기대 동작, 검증 방법은 이를 확인할 테스트·명령 또는 수동 확인으로 구분한다.
- 구현 파일·클래스 구조·사용 예시는 확인되었거나 필요한 수준까지만 적고, 미정인 설계를 문서 분량을 채우기 위해 만들지 않는다.

### 2-B. 기존 문서 갱신

파일 편집 도구로 변경된 부분만 수정한다. 전체 재작성 금지.
**중요: 영어 섹션과 한국어 섹션을 반드시 동시에 갱신하여 내용을 동기화한다.**

**자주 갱신하는 패턴:**

```
# 상태 변경 (영어/한국어 섹션 모두)
"🔲 Not Started" → "🚧 In Progress" → "✅ Completed"
"🔲 미시작" → "🚧 진행 중" → "✅ 완료"

# 완료 항목 추가
완료 예정 항목 테이블의 상태 컬럼 업데이트 (양쪽 언어 섹션)
구현 상세 섹션 추가

# 설계 결정 기록
"Design Decisions" / "설계 결정 사항" 섹션에 항목 추가

# 변경 이력 추가
Change Log / 변경 이력 테이블 하단에 행 추가
```

## STEP 3 — README.md 구조에 Phase 디렉토리 반영

Phase 문서 신규 생성 시 README.md의 프로젝트 구조 트리에 반영한다:

`README_ko.md`가 있으면 대응하는 구조·링크도 함께 반영한다. 관련 부분만 수정한다.

```
├── Phase/
│   ├── Phase1_Foundation.md          # ✅ 완료
│   ├── Phase2_CoreEngine.md          # 🔲 미시작
│   ├── Phase3_OutputGeneration.md    # 🔲 미시작
│   └── Phase4_QualityAssurance.md    # 🔲 미시작
```

---

## STEP 4 — dev-log에 변경 이력 기록

문서 작성/갱신 후 사용 가능한 `dev-log` 스킬이 있으면 해당 지침을 읽고 기록한다. 없으면 Phase 문서의 변경 이력에 기록하고 별도 dev-log는 생략했다고 보고한다. dev-log를 설치하거나 별도 로그 시스템을 만들지 않는다.

```
[dev-log에 기록할 내용]
event_type : CHANGE
module     : PhaseDoc
message    : Phase N 문서 [신규 생성 | 갱신]
before     : [변경 전 상태 요약]
after      : [변경 후 상태 요약]
reason     : [변경 이유]
```

---

## STEP 5 — 완료 보고

갱신된 내용을 아래 형식으로 보고한다:

```
[phase-doc] 완료
- 대상 파일: Phase/PhaseN_[EnglishName].md
- 작업 유형: [신규 생성 | 상태 변경 | 완료 항목 추가 | 설계 변경 | 전체 갱신]
- 변경 내용: [한 줄 요약]
- dev-log 기록: ✅ 또는 생략(미설치/실패 사유)
```

## 출력 형식

### 파일 경로 규칙

파일명은 반드시 **영어 PascalCase**로 작성한다. 한국어 파일명 사용 금지.

```
Phase/Phase1_Foundation.md
Phase/Phase2_CoreEngine.md
Phase/Phase3_OutputGeneration.md
Phase/Phase4_QualityAssurance.md
```

### 상태 표기 규칙

```
✅ 완료       — Phase 내 모든 필수 항목 검증 완료 및 프로젝트에서 요구하는 사용자 인수 완료
🚧 진행 중    — Phase 내 일부 완료, 일부 미시작
🔲 미시작     — Phase 내 전체 미시작
⏸ 보류       — 일정 미정
```

## 실패 처리

| 실패 유형 | 처리 방법 |
|---|---|
| `Phase/` 디렉토리 없음 | 현재 환경의 파일 도구로 생성 후 재시도 |
| 파일 I/O 실패 (읽기) | 경로 재확인 요청 후 중단 |
| 파일 I/O 실패 (쓰기) | 기존 오류 기록 방식이 있으면 기록하고, 실패 내용·대상 경로를 보고한 뒤 중단 |
| dev-log 스킬 기록 실패 | 문서 작업은 완료 처리, dev-log 기록 스킵 후 사용자 알림 |
| 기존 문서 편집 실패 (대상 문자열 미발견) | 해당 섹션을 다시 읽고 정확한 문자열로 재시도 |

## 주의사항

- 기존 문서가 있으면 반드시 먼저 읽고 수정할 것
- 전체 재작성 대신 변경된 부분만 파일 편집 도구로 수정할 것
- 스킬/모듈의 실제 구현 내용을 반영할 것 (설계 예정 내용과 구분)
- 완료 항목 기록 시 소스 코드의 실제 클래스/함수명을 필요한 경우 정확히 기재
- 테스트·리뷰 결과는 확인한 근거만 기록한다. 실패·미실행·중단·테스트 미발견을 통과로 표시하지 않는다. 기술적 완료와 프로젝트에서 요구하는 사용자 인수를 구분한다.
- `변경 이력` 섹션은 항상 최신 날짜순(하단 추가)으로 유지
- **문서는 상단 영어 → `---` 구분선 → 하단 한국어 이중 언어 구조를 유지한다**
- **갱신 시 영어/한국어 양쪽 섹션을 반드시 동시에 수정하여 내용 동기화를 유지한다**
